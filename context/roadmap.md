# Beamlet — roadmap

**Status:** The work agreed, anchored to versions, in order. Each step gets a planning pass that pins its spec before implementation. What is settled lives in `design.md`. Beamlet is beta until 1.0; a 0.x minor may change any surface and says so in the changelog.

**Last updated:** 2026-10-03 (verification before the release, step 15; use after it, step 17)

Steps 1 to 8 and 10 to 13 are done and step 9 dropped; design § 2 Login and OAuth, The owner, tokens and principals, Two databases, Web, Config, Deployment, Define, Patch, Discovery, Policy and MCP hold what they settled.

2. **Login and the `/beamlet` namespace.** Done 2026-09-21. Passwords on users with a no-echo prompt, the cookie session, `Beamlet.Web.Auth`, the sign-in and sign-out, `/beamlet` behind the login, the web pieces under `Beamlet.Web`.

The token table's two kinds and the CLI addressing tokens by id; the 401 challenge and the two discovery documents; the guarded client fetch, the code store, the consent page and the token endpoint with both grants.
4. **User-bounded policies.** Done 2026-09-22. A user carries the policies its tokens may name; one gate in `Beamlet.Users` for the CLI, the consent page and the token endpoint; the plug refuses a token outside its user's list. Reversed 2026-10-01: a beamlet has one owner, and policy attaches to the token alone.
5. **Home page and design pass.** Done 2026-09-23. The setup page with a tab per client; the built stylesheet carrying the design system's tokens and the shared components; live reload of the library in development; every view a LiveView, the sign-in and consent pages included.
6. **Operator config file.** Done 2026-09-23. `Beamlet.Config.Provider` in the library merges an optional `<data_dir>/config.exs` into application config at boot, listed by the server's release, so a container declares policies without a rebuild (design § 2 Deployment). Both `dev.exs` files import `data/config.exs` when it exists, so the dev policy is declared once and the trap of `explorer` in both projects' dev config is gone.
7. **Furniture upgrades.** Done 2026-09-23. `Beamlet.Tables` is an ordered list of up-only steps over `PRAGMA user_version`, run at boot, each step with its version bump in one transaction; a file above the current version fails the boot (design § 2 Two databases). Step one creates `__kv` and `__routes`. Tests prove a file at version zero reaches the current one and a newer file is refused.
8. **`beamlet reset`.** Done 2026-09-23. A CLI command wiping the agent database, the code dir with its git history and the files dir, all or nothing, keeping users, tokens and the config file. It detects no running beamlet and says to restart one: the CLI is always its own VM, and a probe over distribution would block Fly (design § 2 Users, tokens and principals).
9. **`beamlet eval`.** Dropped 2026-09-23. The read it was for is already `bin/beamlet_server rpc 'IO.puts Beamlet.MCP.Server.server_instructions()'`, `bin/beamlet_server remote`, or `iex -S mix phx.server` in development; step 13 documents those. A second beamlet booted in the CLI's VM would race the running one on the code dir, and a distribution link needs a node-naming convention in development; neither earns its place for that read.
10. **CI and the image workflow.** Done 2026-09-23. `ci.yml` runs on pushes and pull requests to `main`: the library's `mix precommit` over OTP 28 and 29 against Elixir 1.19 and 1.20 (1.19 on 29 excluded), the server's with no tests, each followed by `git diff --exit-code` since precommit fixes rather than checks. `release.yml` runs on a version tag: CI, a check that the tag matches both `mix.exs` versions, native amd64 and arm64 builds merged into one image on GHCR (design § 2 Deployment). `fly.toml` runs the published image. Both projects require Elixir 1.19. A `v0.1.0-rc.1` tag proved the workflow end to end, after fixing what the wider matrix and CI timing turned up: the 1.19 config reader, the curation guards pinned to the image's platform, git's detached maintenance racing a wipe, and an order-dependent test.
11. **Patch.** Done 2026-09-29, in five phases from 2026-09-27. Editing modules in place: the module as the unit of `define` with source stored formatted and one locator form for every error; `print_outline` and function and range reads; a function-level summary under every replace; the `patch` tool with `find` and `select` anchors, applied as one transaction through the define pipeline behind a stale-read hash; scattered clauses refused; and `define` as two tools in one in the policy, with `print_policy` the one place naming which tools a token has. The 0.1 walkthroughs (step 15) are where to measure what it buys: `git log -p` in the code dir shows every hunk the transcript did not ask for, and a model re-emitting a module whole after a compile error is the count behind the deferred drafts.
12. **Code review.** Done 2026-10-01, reviewed 2026-09-29 and fixed in batches after. Bugs and sloppy code across the library and the server, with a security read of the login and OAuth surface. It settled the security model, recorded in `security.md`: any token is full access, and policies are guardrails, not containment. So a beamlet became single-owner, tokens became the owner's delegations, and provenance keys on the token. Escapes past a policy were closed only where the fix was cheap or completed an existing rule; `Host.HTTP` was slimmed to the outbound guard's home. The rest were robustness and readability fixes, recorded in design where they changed a decision. One finding is deferred to 0.4: script on an agent page driving the consent page as the signed-in owner. A second pass before release (2026-10-02), a security review against `security.md` and a quality review beside it, fixed what should land before 0.1.0: crashes on parse errors and bad input, route rows served in mount order, refreshed on define and pruned when Ecto or Phoenix cannot take them, eval memory and output bounded while the code runs, OAuth codes hashed, the code lane waiting with its caller's lifetime, and the teaching copy at the common slips; `security.md` records what it found accepted.
13. **Test review.** Done 2026-10-03, reviewed 2026-10-02 and fixed in seven batches. The suite went from 43.8s to about 24s with no loss of isolation, by sorting tests on what they change: pure tests take no beamlet and run async; tests that change only rows share one beamlet per module (`use Beamlet.Case, shared: true`), the sandbox isolating them and a check after each test failing one that defines code; tests that change code keep a beamlet each, booted from a copy of the run's first code dir so a boot runs one git command rather than three, with the compiled-in placeholder router restored before each. About forty tests that restated the implementation or a neighbour went, a handful of security tests that could not fail were rewritten, the public functions that existed only for tests were removed, and the `security.md` claims no test reached got tests, the server's among them: `server/` has tests of its own, run by its precommit and so by CI. It fixed one bug, a reference to a generated module recording no dependency on its owner (design § Define), and brought the endpoints in line: `MethodOverride` joins what a host carries, and the server dropped its multipart parser, whose uploads agent code cannot read (design § Web; uploads under 0.4). ## 0.2 — concurrency

Supervised processes for agent code, and async tasks inside an eval. Shape from the omni_host M15 note: a beamlet-owned supervisor agents register children into, a durable record of what should be running, boot restart, teardown verbs, a `Host.*` face. Not a policy row: a bare `allow Task` yields processes that die with the eval or leak. The process-primitive closure in the signage becomes a redirect.

## 0.3 — static assets

Agent-served files and agent-installed JavaScript and CSS, colocated JS and CSS in agent modules as the likely shape (design § 4). `Beamlet.Assets` is where served files grow. Open: where npm packages live and who runs the install; the `root_tag_attribute` setting colocated CSS needs in the compiling VM.

## 0.4 — admin UI

LiveViews in the library under `/beamlet`, beside the home page and behind the login: files with drag-and-drop upload, routes, read-only source for modules. Uploads to agent routes belong with the files work: the server dropped its multipart parser at step 13, since `Plug.Parsers` writes uploads to the system temp dir, where agent code cannot read them (`File` is denied, `Host.File` is scoped to the files dir). Supporting them means the multipart parser back in the endpoint list and a `Host.*` function moving an upload into the files dir. Sensitive actions ask for the password again, and the consent page's Allow asks for it every time, signed in or not, with client ids on the beamlet's own host refused. Agent pages share the beamlet's origin and the browser sends the app's cookie to any `/beamlet` request, so script on an agent page can otherwise drive the consent page as the signed-in owner. A separate origin for agent pages is the complete fix, if pages are ever shared publicly.

## 0.5 — agent-installed dependencies

Hex packages at runtime: propose, operator approves, the beamlet installs, the policy grants. A durable manifest with git-audit treatment, applied at boot before the code dir compiles; `Mix.install` is once per VM, so a change means a restart. Reopens the trusted-owner security posture (`security.md` § 7), and brings a package-level grant (`allow_app`, declined at step 9 of the port).

## Deferred

Design § 4 holds the list. Three follow-ups with no version: a walkthrough run on a local model, on the same script; the modern-era MCP protocol (2026-07-28), waiting on Anubis; and drafts for failed defines (2026-09-27). A define that fails to compile leaves nothing behind, so the fix is a whole re-emission, the cost patch removes for working modules and probably the commoner case, since first defines fail more often than working modules need edits. The narrow shape: a failed new define is kept, quarantined, which already means source on disk with no beam, listed with its error, readable, patchable and removable; a failed replace stays discarded, since with patch in hand the right move is to patch the live module. Open if it proceeds: quieter copy than the operator's quarantine warning, whether git records the attempt, per-module staging for a multi-module call, and that a draft has no author. Failed defines leave no trace, so the walkthrough transcripts are the only measure of how often a model re-emits after a compile error, and that number decides whether it earns a step.

Disconnecting open app pages on a new password (2026-10-01). A sign-out disconnects the app's LiveViews on its session, but a new password set by `beamlet setup` cannot: the CLI runs in a VM of its own with no way to the server's PubSub. Every session is still deleted, so the next reload or reconnect goes to the login; until then an open page looks signed in and its events still run, a consent page's Allow among them. Rare: the password seldom changes, and the page is in the owner's own browser. The ways to close it, should it matter: the CLI reaching the server over distribution, which `mix phx.server` does not offer, or each app page checking its session before an event or on a timer.

Security minors from the review (2026-10-01), unscheduled, each small:

- The PKCE `code_verifier` is not checked for length and charset (RFC 7636: 43 to 128 unreserved characters).
- Refresh reuse goes unflagged: the compare-and-swap stops a race, but a thief who redeems first keeps the token. Detection, revoking a token when a rotated secret comes back, needs previous refresh hashes kept.
- Anubis session state holds `req_headers`, so a session crash report could log the bearer (suspicion).
- The server's `Plug.RewriteOn` trusts `x-forwarded-proto` from any client when no proxy sits in front.

Suspicions from the pre-release review (2026-10-02), unreproduced, each with a rare trigger:

- A failure past the commit point in `Beamlet.Code.commit/2`, such as a `File.rename!` on a full disk, raises in the server after some files have moved, so the restart boots a partial define.
- `Host.Migrator.migrate/0` prints "Applied" when `Ecto.Migrator.up/4` answers `:already_up`, as two evals migrating at once would.
- `Host.Router.unmount/2` deletes the rows before regenerating, so when regeneration fails the routes stay served until the next one, though the rows are gone and the error says they were unmounted. That branch has no test, left until this is decided, since a test now would pin the behaviour.

Minors from the test review (2026-10-03), confirmed, each small:

- A `schema_migrations` row whose `inserted_at` does not parse, which raw SQL can write, makes `Host.Migrator.print_migrations/0` and `migrate/0` raise Ecto's raw `ArgumentError` ("cannot load ... as type :naive_datetime") until the row is deleted by hand; defines still number past it. A token holder breaking their own migrator; the fix is reading `inserted_at` as text and showing what cannot parse.
- `Beamlet.Eval.run/3` matches `{:ok, policy}` on `Beamlet.Policies.fetch/1`, a `MatchError` for an undeclared policy: unreachable through the plug, reachable by the in-process caller design § 4 anticipates.
- `Beamlet.OAuth.Clients.start_link/1` accepts `name:`, but `fetch/1` always calls the module name; and the cache is never swept, growing by each distinct client id fetched while signed in. Owner-only input.

Orphaned compile workers (2026-10-03), confirmed by the step 13 test review and deferred because nothing in normal use triggers it. A define compiles in a task under `Beamlet.TaskSupervisor`, and the parallel compiler inside it runs each module body in a worker it monitors rather than links. When the task dies, the `{:exit, reason}` branch of `Beamlet.Code.compile/3`, the server rolls back and replies "nothing was changed", but the workers run on, and `stop/1` cannot reach them because it finds them through the dead task's monitors. The orphan then does one of two things. It finishes its module, loads it, and blocks forever in `elixir_module:make_module_available/3` waiting for the dead compiler's ack: a leaked process and a module loaded that is not defined. Or it fails, and the `catch` in `elixir_module:compile/7` purges and deletes the module, which on a replace is the previous version the rollback has just restored: the module is gone from the VM until the next boot, its source and beam intact. The task dying takes a bug in the compiler or a kill from outside; agent code cannot reach the compiler's process under the default policy. Timeout and cancel go through `stop/1`, which does kill the workers, except one spawned between its `Process.info(pid, :monitors)` and `Task.shutdown`, a window of microseconds at a moment the compiler has usually spawned them all. The fix, about 20 to 40 lines replacing how `stop/1` finds the workers, then killing and awaiting them on every failure path before the rollback: either each worker records its pid from the tracer, which runs in every compiling process, leaving a race for a worker that has not traced yet; or the failure path scans processes for `:elixir_compiler_info` naming the task, with no race but leaning on a private key of Elixir's. Either way the rollback must also unload modules a killed worker had already loaded, which the dead task's `each_module` callback never recorded. Two tests come back with it, in `code_test.exs` under `define/3`. The seam is a module body that kills its own compile:

```elixir
{compiler, _worker} = :erlang.get(:elixir_compiler_info)
send(:crash_probe, {:worker, self()})
Process.exit(compiler, :kill)
```

with the test registered as `:crash_probe` and the entries handed to `Beamlet.Code.define/3` unscanned. Each test awaits the worker's `DOWN` before looking. A new module: the reply is `{:error, "define failed (:killed) — nothing was changed"}`, and no file is under `lib/`, nothing is defined or loaded, and the server is alive. A replace of a module defining `version/0` as 1 with one defining it as 2 after the kill: the same reply, `version()` still 1, the file unchanged. Today the first fails on the loaded module and the leaked worker, the second on the module being gone, six runs of six.

Protocols, maybe (2026-09-30). Full support for agent-defined protocols and for agent implementations of library ones (`defprotocol`, `defimpl`, `@derive`), all refused by the scanner today. An agent's own protocol is the easy half: compiled at runtime it is never consolidated, so it dispatches dynamically and its implementations would work as loaded. Implementing a library protocol is the hard half, because Mix consolidates protocols at build into a fixed list of implementations and one loaded later is never dispatched to. Two routes, the choice open:

- **No consolidation.** `consolidate_protocols: false` in the server, and asked of embedders. Simple, and runtime implementations just work. Every protocol dispatch in the VM gets slower (`Enum` over non-lists, JSON encoding, Phoenix rendering), Elixir advises against it, and Beamlet cannot impose it on an embedder.
- **Re-consolidation at runtime.** `Protocol.consolidate/2` builds a protocol's binary for a given implementation list; proven in a spike (2026-09-30) by deriving `Jason.Encoder` at runtime, re-consolidating and hot-loading it. Costs: releases must keep the debug info chunk consolidation reads, which `strip_beams` removes today, and embedders must too; the code server tracks agent implementations per protocol and re-consolidates on every define, replace, remove, rollback and boot that changes the set; it rewrites library modules VM-wide, the host's `Enumerable` when embedded, the first time agent actions would; and the scanner needs rules for a nested `defimpl` against a granted protocol with a literal `for:`. M to L, mostly the code server.

Demand today is `@derive Jason.Encoder` for JSON APIs, which building a map covers, as Phoenix's generated JSON views already do.
