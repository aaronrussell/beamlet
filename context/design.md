# Beamlet — design

**Status:** Working note, deliberately light. It records what is settled and why, one decision at a time as the code lands. Nothing is carried over from `../omni_host` unexamined. History lives in git; this note keeps the decisions and the reasons that still bear on the next one, and an alternative only where someone would plausibly propose it again.

**Last updated:** 2026-09-23 (login and OAuth folded in from its feature note; cleanup)

---

## 1. Framing

**Name:** Beamlet. **Package:** `beamlet`.

*A little Elixir server to make your own.*

Beamlet is a programmable Elixir code server for AI agents. Agents can define modules, execute code, and build APIs and live dashboards inside a running application. Available as an embeddable Elixir package and a standalone MCP server, independently of Omni.

A small, persistent computing environment to tinker with, not a disposable code runner. Primarily for Elixir developers having fun building things with agents, rather than an enterprise automation platform. The tone is friendly, curious and technically fluent: playful without being childish, concrete rather than full of AI hype.

### Language

- **Beamlet** is the project.
- **A beamlet** is a running instance.
- **My beamlet** is where your code and applications live.

The name works in prompts: "What routes exist on my beamlet?" "Add a dashboard to my beamlet." The agent works *on* your beamlet; it is not the beamlet. Different agents and clients interact with the same environment.

"A beamlet" is the only new noun. Everything else stays ordinary: modules, routes, tools, applications, users, tokens.

### Why the name

Short, memorable, connected to the BEAM. The diminutive suggests something approachable and personal, a little computer you can make your own. It names the thing itself without "server" or "instance" appended.

## 2. Settled

Each entry is a starting position, held until the code says otherwise, dated when it was settled.

### One package, one nested server

```
beamlet/                 the repo and the hex package
  lib/host/              Host.*          agent-facing stdlib
  lib/beamlet/           Beamlet.*       machinery, databases, users, web pieces
  lib/beamlet/mcp/       Beamlet.MCP.*   Anubis server and tool components
  server/                beamlet_server  the standalone Phoenix app, path dep on `..`
  Dockerfile             builds and runs the server
  fly.toml               one machine, one volume, for the image on Fly
```

The library is a **child spec** a host starts in its own supervision tree; it declares no OTP application of its own. This keeps boot ordering in the host's hands, lets tests start and stop a beamlet per test, and makes the standalone server the smallest possible consumer rather than a special case. `start_link/1` takes `only: :system` to start the policies and the system database alone, migrated, which is what the operator CLI needs in a VM with no beamlet running; the knowledge of a beamlet's processes stays in `Beamlet.init/1`.

The server test: `server/` holds nothing a second embedder would want. Endpoint, application module, config, release, Dockerfile. Anything else belongs in the library, the admin UI included, which ships as LiveViews in `Beamlet.Router`.

### Two surfaces

`Host.*` is what agent code reads and calls. `Beamlet.*` is what the operator and the embedding host use. The name `Host` is kept from code mode on purpose: it reads well ("the host of my code") and agent-facing vocabulary is the most expensive thing to rename once it lives in docs, teaching errors and model habits.

**Where the machinery behind a `Host` module lives** (2026-09-16). `Host.X` is the agent surface: it prints, raises with teaching copy, returns plain values, and is granted wholesale by the policy, so it holds only what an agent may call. The implementation sits in a root-level `Beamlet.*` module only when it earns its place: something else in Beamlet calls it, or it is a real subsystem, a context over a table, a process, a generator. Otherwise `Host.X` is the whole thing. The two sides share a leaf name when they are the same thing seen from each side (`Beamlet.Code` and `Host.Code`, `Beamlet.Repo` and `Host.Repo`), and a table follows the context convention (`Beamlet.Routes` owning `Beamlet.Route`, with `Host.Router` as the agent face). A support module has a moduledoc when an embedder might call it and `@moduledoc false` otherwise. Nesting the implementation inside the `Host` module lost: it puts machinery in the agent's territory, where the listing, the reserved-prefix check and the moduledoc rule would all need a special case. Nothing under `Beamlet.*` is granted, so the split is what keeps the machinery out of reach by construction.

**Where a schema sits** (2026-09-17). A schema that is a resource of a public context sits at the root beside it, singular: `Beamlet.User` beside `Beamlet.Users`, `Beamlet.Route` beside `Beamlet.Routes`. A schema that is a private detail behind a `Host` module with no context nests under that module's internal namespace with `@moduledoc false`: `Beamlet.KV.Entry` is the encoding of `Host.KV`'s rows and nothing outside the module touches it. One rule, applied to a public resource and to an implementation detail.

### Two databases

Both Beamlet's, both under the data dir:

- **Agent database** (`Host.Repo`): tables agents migrate and query, the key/value table, and the route table. Everything an agent builds, so it wipes and backs up as one unit.
- **System database** (`Beamlet.Repo`): users and tokens. Migrated by Beamlet itself at boot from the package's priv dir.

Both live under `db/` in the data dir, `agent.db` and `beamlet.db`, with SQLite's `-wal` and `-shm` sidecars beside them. The paths are derived, never configured; adapter options for either repo go under `config :beamlet, <Repo>`. Boot creates each file in WAL mode with a single connection before its pool starts, because a pool opening several connections on a file not yet in WAL mode races to switch it and logs failed connects; `mix ecto.create` would not prevent this, since `storage_up` ignores the adapter's WAL default, so the journal mode is explicit in each repo's `init/2`. The `Ecto.Migrator` child migrates the system database at every boot in every environment, so no consumer runs a migration step and the test suite needs no `ecto.migrate` alias. An authorizer on every agent database connection refuses `ATTACH` and `DETACH`, so raw SQL granted to agents stays inside that file (`Beamlet.SQLiteAuthorizer`).

**Beamlet's own tables in the agent database** (2026-09-17) are created by `Beamlet.Tables`, a synchronous child right after `Host.Repo` that runs `CREATE TABLE IF NOT EXISTS` for each and returns `:ignore`, so a failure fails the boot and a table agent code dropped is back at the next one. The double-underscore names (`__kv` and `__routes`) mark them as furniture: Beamlet's tables holding the agent's data, outside the agent's migration history and inside the unit that wipes and backs up. A second `Ecto.Migrator` over `Host.Repo` lost: `migration_source` is repo config, so the agent's migrations would share it, and Beamlet's history would sit in the agent's database beside theirs. From 0.1 the tables are versioned (roadmap 0.1 step 7): `PRAGMA user_version`, the integer SQLite keeps in the file header, and `Beamlet.Tables` as an ordered list of up-only steps that runs the ones above the stored version at boot and stores the new one, with no tracking table and no change to either Ecto migrator, so a beamlet skipping several versions runs every step between. That trades away the free recreation of a dropped table, accepted. The promise from 0.1 on: an upgrade never requires a fresh data dir. The system database migrates through Ecto, the furniture through these steps, a change to the code dir or files dir layout ships the move that applies it, and the agent's own tables are never touched.

### Users, tokens and principals

Settled 2026-09-14, the two token kinds 2026-09-21. The vocabulary first, because the words do the work:

- A **user** is a row in the system database: the durable name the operator creates and the history refers to. Id, name, an optional password for the browser, the policies it may carry (below), timestamps. No roles, no email.
- A **token** is a credential belonging to one user: a random secret shown once at creation and stored as a hash, with a **policy**. A user has many, one per client or device, and the same person holds a permissive token and a restricted one and uses them in different places. Delete is delete; nothing references a token row, so there is no revoked state. Two kinds: a `cli` token is named by the operator, never expires and is how the operator's own code connects; an `oauth` token is minted at consent, carries the client id URL as `client`, expires and is refreshed. `Beamlet.Token.label/1`, the name or the client's host, is how either is shown.
- **Authentication** turns the bearer token on a request into its token row and user. It happens once per request, at the edge, and only Beamlet's own tokens are valid.
- The **principal** is what a request acts as: user id and name, token id and label, policy name. Built per request from the token, never stored. Every exec, define, commit and route keys on it. The client's name and version are not on it: they are connection metadata, the token is the provenance, and a user knows where each of their tokens is used. `Beamlet.Principal` is flat, five fields; the encodings below do the nesting.
- **Authorization** is checking what the principal may do, forward looking: the scanner enforcing the policy. **Provenance** is the record a persisted thing keeps of the principal that made it, backward looking. "Identity" is not a term of art here; the principal covers it.
- The **system principal** is what the beamlet acts as on its own behalf: user and token both named `beamlet` with id 0, which the database never issues, under `default`. Named `beamlet` rather than `system` because that is the name already on every commit's committer line, so a reader of `git log` sees one name for the beamlet itself; the user name is reserved in the changeset. The boot sweep uses it, so every commit carries trailers and the audit has one shape of commit, and it is the seam a future in-process embedder would hand in. Nothing falls back to it: a `Host.*` function that needs a principal and finds none raises, since the unanticipated case should be loud.
- **A principal is a token acting through a tool; a web identity is a user on a request; nothing turns one into the other** (2026-09-17). The principal carries a policy because the tools are where code is authored and discovered, and the policy governs exactly those two things; it is ambient in the process only because evaluated code takes no arguments. A served route is neither: its code was scanned when it was defined, under its author's policy, and nothing more is authored when it runs. So a route acts as nobody, the `Host.*` functions that record who acted or filter by policy raise inside one, and a controller action that removes modules or unmounts routes is not a supported case. A signed-in person is a web identity: a user known to the request, carried on the conn or the socket the way Phoenix carries `current_user`, with no token and no policy, since a browser authors no code. If a page ever changes the beamlet, that is the admin UI calling `Beamlet.*` with an explicit record of who acted, not agent code reaching for tool-side verbs.

**Policy attaches to the token, not the user.** A policy is a named document (§ 2 Policy says what it contains); Beamlet ships `default`, a token names one and has `default` when it names none. Two policies for one person means two tokens, and the history names both the user and the token, so nothing is lost. A request whose token names a policy the config no longer defines fails clearly rather than falling back.

**A user bounds what their tokens may carry** (2026-09-22). A user carries `policies`, a list of declared policy names, `{:array, :string}` stored as JSON text on SQLite; empty means every declared policy, so the one-user beamlet has no ceremony and the restriction is opt-in. Without it, anyone with a password could pick the most permissive policy on the consent page. Policy still attaches to the token; the list is a bound on the user, set by the operator: `users.create --policy`, repeatable, `users.update --policy` replacing the list whole and `--all-policies` clearing it, and `users` showing the list or `all`. `Beamlet.Users.policies/1` is the one reading of "empty means all", and `create_token/2` and `update_token/2` are the one gate, which the CLI, the consent page and the token endpoint all mint through: a policy outside the user's list is a changeset error on `policy` naming what the user may use, read as a field rather than a change so that a `cli` token naming nothing, which would take the schema's `default`, is refused for a user whose list lacks it. The CLI says so before it mints: `tokens.create` without `--policy` for such a user names the list and the flag. The consent page lists only the user's policies, `default` preselected when on offer and the first otherwise, and the token endpoint answers a refused mint as `invalid_grant`. `Beamlet.MCP.Plug` applies the bound on every request: a token whose policy is outside its user's current non-empty list is a 403 naming the token, the policy and the user, so narrowing a list takes effect on the next request and the operator never hunts down old tokens. For the same reason `users.update --policy` does not refuse to drop a policy that existing tokens carry: it counts the tokens now outside the list and says the beamlet will refuse them until they are updated or deleted.

**Identity is per request, with no session binding.** The protocol is heading that way (the 2026-07-28 revision removes sessions) and nothing here needs the alternative: server instructions never depend on the token, so `print_policy` under the request's own token is how a client learns what it may call.

**Management is operator-only.** The public functions of `Beamlet.Users` are the product; `Beamlet.CLI` is a thin shell over them. Nothing under `Host.*` creates, lists or deletes users or tokens. `Beamlet.Case` creates a user, `alice`, and one token for every test through the same functions, so every test authenticates the way production does.

The CLI is one function, `Beamlet.CLI.main/1` over argv, printing plain text and returning `:ok` or `:error`, and each environment gets a thin entry that calls it: `mix beamlet` in development, `bin/beamlet` in the release, which has no Mix, so the module is the one implementation. Commands are dotted, `users.create USER`, `tokens.create NAME --user USER`; users are addressed by name and tokens by the id `tokens [--user USER]` prints, since an OAuth token has no name; `tokens.update ID` takes a `cli` token only and `tokens.delete ID` either. Delete asks nothing and says what it removed. The CLI needs the policies and the system database and nothing an agent reaches: when no beamlet runs in the VM it starts that half of one with `Beamlet.start_link(only: :system)`, runs the command and stops it, so it works beside a beamlet in another VM or with none at all, and a bad policy declaration fails the command with the boot's own error; a beamlet in the same VM is used as it is. `policies` lists the declared names and `policies.show NAME` renders one.

**One context, structs at the root.** `Beamlet.Users` owns users and their tokens, with `Beamlet.User` and `Beamlet.Token` beside it. A token is a sub-resource of a user in every way that matters: it belongs to one, dies with one, and is created and listed through one. The tell was the arguments. Plain `create`, `update`, `delete`, `list`, `find` and `find_by` take conventional arguments, attrs and structs, so they stay predictable as fields arrive; a token function takes the user it belongs to, which is what makes it a user operation (`create_token(user, attrs)`, `list_tokens(user)`), and `authenticate` turns a secret into its token with the user loaded. A separate `Tokens` store was tried first and read wrong for exactly that reason. The structs stay at the root rather than under the context because `Beamlet.Users.User` stutters. Ecto's own shapes throughout: a failed validation returns the changeset, a miss returns `{:error, :not_found}`. User and token names follow one rule, lowercase letters, digits, underscores and hyphens, at most 64 characters, because a user name becomes a git author email and both appear as trailer values. A token name is unique per user, not per beamlet. The policy default lives on the schema, not the column, so the database records no design decision.

The secret is 32 random bytes as unpadded URL-safe base64, the string a client keeps. Only its SHA-256 is stored, a raw binary under a unique index; a fast hash is right for a secret with that much entropy. `Beamlet.Users.authenticate/1` hashes the presented string as it is, with no decoding step, so a malformed value simply matches nothing. The secret rides on a virtual field of the struct that `create_token` returns and is nil on every token loaded afterwards.

**Tokens are opaque, in one table with a kind** (2026-09-21). A JWT access token needs a signing key that survives restarts and a JOSE dependency, and cannot be revoked before expiry without a denylist, so it needs short lifetimes and therefore stored refresh tokens: the table comes back holding refresh tokens instead of access tokens. What a JWT buys is validation by a process that cannot reach the store, which a single-node beamlet never needs. An opaque secret with its hash in a local SQLite file validates in one indexed read, needs no key, and gives CLI and OAuth tokens one row shape. The `kind` is an `Ecto.Enum` column, `cli` or `oauth`, not a reading of which fields are null, because the kinds differ in several columns already and an implicit rule breaks the day another arrives. A `cli` token has a `name`, required, unique per user and under the name rule since it lands in a git trailer, and null expiry and refresh fields. An `oauth` token has `client`, the client id URL verbatim, the identity the redirect was verified against, since anyone can host a document that says "ChatGPT"; `expires_at`, `refresh_hash` and `refresh_expires_at` required; no name; and nothing unique on `client`, since a person may authorize the same client twice. Two honest columns beat one overloaded. Refresh rotates in place, new secret and refresh hashes on the same row, so the token id provenance points at survives. Two changeset functions, `cli_changeset/2` and `oauth_changeset/2`; the context picks by kind, and the token endpoint refuses to refresh a `cli` token. The principal carries `token_label`, so a trailer reads `Token: laptop (3)` or `Token: claude.ai (7)`.

### Policy

Settled 2026-09-15. Code mode had three mechanisms at three scopes: grants as host-wide config, shape rules per agent, tool access per agent. In Beamlet all of it is one document, and a token names one.

The vocabulary:

- A **policy** is a named document saying what a token's requests may do on a beamlet. Three parts: tools, rules, grants. One name answers the question.
- **Tools** are which of the beamlet's MCP tools the token may use, `eval` and `define` today.
- **Rules** are the shape rules on submitted code, `allow_defmacro` and `allow_dynamic_dispatch`, strict by default. They are submission rules, not execution rules: they govern what a token may author into the shared pool, never what it may call.
- **Grants** are the name table: a module maps to `:all`, `only` or `except` at function/arity granularity, and absence is denial. The verbs are `allow` and `deny`.
- **`default`** is the policy Beamlet ships: the curated grants, strict rules, both tools. It cannot be declared or changed, every other policy builds on it, and a token has it when it names none.
- The **effective grants** are a policy's grants plus every defined module, granted by existence. The shared pool is the one thing that is not per policy: anything one token is granted reaches the pool through a module it defines, as a macro does under `allow_defmacro`. Accepted once, here, and documented for the operator; not a reason to withhold the lever.
- **Signage** is the teaching copy appended to a refusal, for the few names where "not permitted by your policy" would leave an agent guessing. It is Beamlet-wide, not part of any policy, and a lookup takes the policy so the copy stays true for it.
- The **curation record** is the data behind `default` and the coverage walk that proves every documented platform module has a ruling.

Two kinds of signage earn a place. A **redirect** names the door the agent would not guess: `File` is refused, `Host.File` is where scoped file access lives; likewise `Host.KV` for `Agent` and the ETS family, `Host.Repo` for `Ecto.Repo`, `Host.Router`, `Host.PubSub`, `Host.Migrator`, and the `define` tool for `Code`. A **closure** says a whole family is withheld, so the agent stops walking its siblings; it pays for itself only over a family the model predictably walks, process primitives and the environment (with the reason it may hold credentials, which changes the agent's plan). A policy that grants a signed module never refuses it, so its hint never fires; a redirect whose door the policy withholds is dropped, since a pointer at a closed door is the one hint that misleads. Everything else denied gets the generic copy, and the not-granted record carries the reason.

Retired words: *stance*, *amendment*, *whitelist*, *name policy*, and *code mode* in anything an agent reads, where a refusal says "not permitted by your policy".

**A policy is data, declared in application config, validated and resolved at boot, never stored.** Not a file the library reads, not a module, not a row:

```elixir
config :beamlet,
  policies: [
    explorer: [
      tools: [:eval],                          # replaces the default's list
      rules: [allow_dynamic_dispatch: true],   # merges into the default's rules
      allow: [Task, {File, only: [read: 1]}],  # replaces the module's entry
      deny: [Host.Repo, Req, Req.Request]      # removes the entry
    ]
  ]
```

Config is already the one surface, read at runtime, so an embedder writes this in their own config and a release sets it from `runtime.exs` with nothing new to learn. Validation is a function over data: a teaching error names the policy and the key and fails the boot. The alternatives each lost on one point. A DSL file in the data dir is a second declaration surface that evaluates code at boot for what is a document. Rows in the system database suit things the product creates at runtime, and a policy is authored; a dozen entries through CLI flags ends in an import command, at which point the file is the truth and the row a stale copy. A module suits an embedder and is unreachable from a container.

The document, applied as `default`, then `allow`, then `deny`:

- `tools` replaces the default's list when given.
- `rules` merges: a key given overrides, a key absent stays strict, an unknown key fails the boot. New shape rules get a home here without widening the top level.
- `allow` replaces the module's entry wholesale, the default's included, so `allow: [Kernel]` re-enables `apply`, the operator's deliberate call. `only:` and `except:` are relative to the module's full surface.
- `deny` removes the module's entry. It applies after `allow`, so a module in both keys is denied, documented rather than an error; denying a module nothing grants is a no-op.
- Order inside a key does not matter, a module named twice in one key is an error, every module named must be loadable on the beamlet, and every function under `only:` or `except:` must be exported at that arity, as a function or macro, so a typo fails the boot rather than granting nothing.
- Policy names follow the user and token name rule; `default` is reserved.
- Declare and restart. No reload.

Two keys were considered and left out. `extends` between custom policies: every policy extends `default`, and chains are a speculative need. `allow_app`: which packages exist is a property of the runtime, not of a policy. The default grants the packages the beamlet ships, `jason` and `req`, each expanded at boot into per-module entries with `@moduledoc false` modules excluded. Jason stays beside Elixir's `JSON` because models reach for it by training, and turning them away teaches nothing. A custom policy speaks only in modules; an embedder granting their own package lists its modules under `allow`, and agent-installed dependencies (§ 4) will decide who grants those. `deny` is per module, so closing HTTP for a policy names the package's entry points, `Req` and `Req.Request`, which is short for any package; a `deny_app` can arrive when a policy needs it. The default also grants every `Host.*` module whole, the framework's web and data rows, and `Macro`'s string helpers (`underscore/1`, `camelize/1`, `to_string/1`); everything that builds or expands code stays denied.

**Enforcement** sits at three edges and one gate:

- **Tools.** The listing is per request: `Beamlet.MCP.Server` overrides `handle_request/2` to filter the `tools/list` reply by the principal's policy and to refuse a `tools/call` for an ungranted tool before dispatch, delegating everything else to Anubis. A listed tool is a promise, and a model that never sees `define` never reaches for it. The refusal is the JSON-RPC error Anubis returns for a tool that does not exist, since to that token it does not; an HTTP error on a `tools/call` POST would read as a transport failure to a client. Anubis's own per-component `scopes` reads only its OAuth claims, which Beamlet does not use, so under Beamlet's plug they are always empty. No list-changed notifications: a policy change is a restart.
- **A missing policy.** A token naming a policy the config no longer declares is a 403 from `Beamlet.MCP.Plug` on every request, with a one-line body naming the token and the policy, the shape of the 401 beside it. The token authenticated and the server considers the credential insufficient, which is what 403 means. Failing at `initialize` is what makes it visible to the person connecting the client.
- **The token.** `Beamlet.Token`'s changeset validates the policy name against the declared names (`Beamlet.Policies.names/0`), so the store refuses a token for a policy that does not exist and the CLI's error comes from the changeset. A token whose policy has since left the config is therefore made in tests by writing the row directly, standing in for the restart that removed it.
- **The scanner** is the gate for rules and grants, taking the policy struct. Boot compiles carry no gate, and tightening a policy never evicts a module: adjudication is submission-time only.

`Host.Code.print_policy/0` renders the calling token's policy, by name: tools, rules in force, the deliberate denials it has not re-granted, partial grants. Tool descriptions and server instructions stay static, so an eval-only token reads a sentence about `define` in the instructions while its listing omits the tool, and the copy is phrased to survive that. The same rendering serves the operator as `beamlet policies.show NAME`.

The shape in code: `Beamlet.Policy` holds the struct (name, tools, rules, grants), `build/2` with the document validation, the grant lookups and `render/1`, its moduledoc the operator's reference including what each relaxed rule reaches; `Beamlet.Policy.Rules`, `Beamlet.Policy.Default` (the curation record, its moduledoc rendered from the data, a golden fixture pinning the composed table) and `Beamlet.Policy.Signage` (`hint/2`, `hint/3` and `denials/1`, with a test proving every signed name is denied under the default) sit beneath it. `Beamlet.Policies` is a `GenServer`, the first child of `Beamlet`, that builds `default` and every declared policy in its init and loads them into an ETS table it owns, so a bad declaration fails the boot, a lookup is one read in the caller with no message to a process, and the policies live exactly as long as the beamlet; `:persistent_term` lost on lifetime, since it outlives the supervisor. `fetch/1` and `names/0` are its whole surface, and `Beamlet.Config.policies!/0` reads the declarations. `Beamlet.Scanner` takes the policy struct and nothing else, `scan_eval/2` and `scan_define/2`; the effective grants' other half, every defined module, is merged into the policy by the caller with `Beamlet.Policy.grant/2`. Policy names are strings everywhere outside config, where keyword keys are atoms; the valid tool names are a list on `Beamlet.Policy`, and a test checks the server's components match. A test declares the policies its beamlet has with `@tag policies: [...]`, in the shape config takes, which `Beamlet.Case` puts into config before the beamlet starts and removes after; a fixed set in the test config lost on each test saying what it expects.

Deliberately out: exec limits per policy, since they are how much rather than what and stay ordinary config; reload; operator-added signage; a policy built on an empty table rather than on `default`.

### Provenance

One struct, two encodings. A route row stores the principal as JSON in a map column; a commit carries it as git trailers, with the user as the author (`alice <alice@beamlet>`) so `git log` and `git blame` show a proper name. Both come from the same struct, so they cannot disagree, and both decode back to it:

```
define: Shopping.Item

User: alice (1)
Token: laptop (3)
Policy: default
```

```json
{"user": {"id": 1, "name": "alice"}, "token": {"id": 3, "name": "laptop"},
 "policy": "default"}
```

Names first and ids beside them: the name is what a reader wants, the id is what a program wants after a rename. Time is not in the stamp; git and the row's timestamp already have it. Trailers because git parses them natively, so a future history call filters by token or policy with no code of ours. The route table lives in the agent database, a different file from users and tokens, so there is no foreign key to keep and no discrete columns: the set is small enough to load and filter in memory. What carries provenance is every commit the code server makes and every route row. Not KV entries, not files, and there is no eval log. `Beamlet.Principal.to_trailers/1` and `from_trailers/1`, `to_map/1` and `from_map/1` are the encodings, and `Beamlet.Route.principal/1` reads a row's back.

### Eval

Settled 2026-09-16. `Beamlet.Eval` is the runtime behind the `eval` tool: `run(code, principal, opts)` fetches the policy by the principal's name, scans, evaluates and returns the result or the error as text, and `Beamlet.MCP.Eval` maps the tuple to a tool result. Nothing sits between them: the component is the tool. The output contract: what the code printed, then `=> ` and the inspected last expression, with a refused call, an exception, a timeout or a memory kill as error text that keeps the output printed before it. Each run is a fresh evaluation in the beamlet's VM, empty bindings, no prelude.

**Two processes, tied one way.** Anubis runs every request in a task of its own and answers `notifications/cancelled` by terminating that task, so the tool process is Anubis's. The code runs in a child under `Beamlet.TaskSupervisor` so that the timeout and the heap cap can kill it while the tool process survives to report with partial output; the tool process owns the StringIO for the same reason. The child is not linked, since those two kills would take the tool process down, and a monitor alone cannot tell the child its caller was cancelled, which would leave the code running to its own timeout after a cancel. Erlang has no one-way link, so a watcher provides it: a third process monitors the tool process and kills the child when it goes. Trapping exits in the tool process lost, since it sets a flag on a process Anubis owns and makes the runner answer the supervisor's shutdown itself. Closing the HTTP stream cancels nothing in Anubis 2.0; the notification is the only cancel signal.

**Three limits**, `config :beamlet, eval: [...]`, each named for what it protects: `timeout` (30 seconds) the session, since a session runs one request at a time; `max_heap_bytes` (256MB) the beamlet; `max_output` (16KB) the model's context. The transport's `request_timeout` is derived from the eval timeout plus a margin: it is a call timeout that answers "Server unavailable" and leaves the request running, so it must never fire first. 16KB because inspected Elixir runs three to four bytes a token, which puts a full result at four to five thousand tokens, under Claude Code's 10,000-token warning (its default cap is 25,000, past which it writes the result to a file and hands the model the path), and because the inline tail teaches where a client's file fallback does not. The inspect limits are constants; nobody tunes how one value renders per beamlet. Agents get no per-call limits; `opts` on `run/3` are for tests.

**The ambient principal.** Evaluated code takes no arguments, so the runner puts the principal in the child's process dictionary before the code runs (`Beamlet.Principal.put_current/1`) and the stdlib functions that must record who acted read it back (`current/0`); outside evaluated code it is nil. The value is the principal alone, and the policy is fetched by name. A tool that holds the principal passes it explicitly.

### Define

Settled 2026-09-16. `Beamlet.Define` is the runtime behind the `define` tool, the shape eval set: `run(code, principal, opts)` fetches the policy, scans (`Beamlet.Scanner.scan_define/2`), runs the docs gate (`Beamlet.Code.Docs`) and hands the buffer to the code server; `Beamlet.MCP.Define` maps the tuple to a tool result. The define semantics came over from code mode whole: modules not files, one canonical file per module under `code/lib`, docs enforced because they are the discovery surface, the two collision tiers with `replace: true` as permission rather than assertion, dependents recompiled on a replace and provable breakage refused with nothing changed. The reserved prefixes are `Beamlet.*` and `Host.*`.

**The code server is `Beamlet.Code`**, a GenServer child of `Beamlet` owning `<data_dir>/code` (`lib/`, `ebin/`, `.staging/`, `.git`), with `Beamlet.Code.Tracer`, `Beamlet.Code.Docs` and `Beamlet.Code.Audit` beneath it as internals. `compile_artifact/2` is the derived-source compile the route generator uses: it runs in the server's lane because the compiler options and tracers it swaps are VM-global, records nothing and writes nothing. Remove is the server's second operation and the audit's second commit kind; its mounted-route check sits beside the dependents check so it is atomic with the removal.

**One table.** The server records everything it collects in a named public ETS table it owns: the compile context the tracer reads, the compiled beams, the edges and call records of the compile in flight, the defined set with its paths, and the quarantine, so `manifest/0`, `quarantined/0` and `defined/0` are table reads. The defined set is the effective grants' other half: an eval's scan never queues behind a thirty-second compile, and both runtimes merge it into the policy with `Beamlet.Policy.grant/2`, the same function the scanner uses to grant a buffer's own modules to each other, before scanning. Rows are added before stale ones go, so a scan in flight never sees a defined module missing.

**Cancel is an abort.** The tool process is Anubis's and a client cancel kills it, so the server monitors the caller for the life of the define: a define still queued behind another never starts, a compiling one is stopped and rolled back to the previous beams, and one past the commit point completes. Eval needed a watcher process because its caller must survive the kill of its child; here the server is long-lived and holds the monitor itself. The parallel compiler monitors its workers rather than linking them, so stopping the compile kills the task and the workers it is watching, on cancel and on timeout alike.

**Git is a requirement, not a mode.** The history is the provenance record, and a flag to skip git is a mode where defines leave no trace. A beamlet whose PATH has no git fails to boot with a teaching error, the repo is initialised at boot with the initial snapshot and hand edits swept into a commit of their own, and the image installs git. The repo carries no configuration: every commit names the user as author (`alice <alice@beamlet>`) and `beamlet` as committer through environment variables on the command, with the principal as trailers in the body, and the sweep commits are authored by `beamlet`. The sweep says what it found: one warning listing git's status lines before the "manual changes" commit, since a hand edit to the code dir is unusual enough to surface to the operator, who reads the VM log and nothing the agent sees, and the commit it names is the point to roll back to. Empty commits are allowed so a replace with the same source is still on the record. A test suite boots a beamlet ninety-odd times and each boot pays git's forty milliseconds; a couple of seconds is not a reason to shape the design.

One limit, `config :beamlet, define: [timeout: 30_000]`, the time one compile may take; the transport's request timeout is derived from the larger of eval's timeout and define's call timeout, since a define may wait a full compile behind another before its own. The principal is required on `define` and `remove`. `Beamlet.Case` wipes the code dir before each beamlet starts, so every test boots with no defined modules and a fresh history.

### Discovery

Settled 2026-09-16. `Host.Code` is the agent's discovery entry point and the module teardown verb: `print_modules`, `print_docs` at three arities, `print_source`, `print_policy` and `remove`. The print contract: a `print_*` function prints and returns `:ok`, `remove` acts silently and returns `:ok`, and a failure raises with a teaching message, so it is unmistakable and eval keeps everything printed before it. The rendering is `Beamlet.Code.Discovery`, `@moduledoc false`, returning `{:ok, text}` or `{:error, text}`, since the print contract is not something a test can assert on as text.

**Every function requires the ambient principal** and raises a teaching error without one ("works from eval, where your code acts as you"). The listing and the docs are filtered by a policy only the principal names, and a removal is recorded against one; a call from a web request or a process of the agent's own has neither, and no policy is an honest fallback, since a custom policy may be wider or narrower than `default`. Discovery takes the **effective policy**, the principal's with the defined modules merged in, exactly as the runtimes build it before a scan, so a defined module is granted like any other.

**The listing is `code/lib`.** Four sections, in order: the modules defined with `define`, each with its moduledoc's first line, followed by any quarantined module with its error and the way out (define it again with `replace: true`, or remove it), since the listing is the one place an agent learns why a module vanished; the `Host.*` modules; the framework modules, the curated web and data authoring surface (`Beamlet.Policy.Default.framework_modules/0`); and the libraries, one line per package the beamlet ships, led by its primary module, with any module granted from another package on a line of its own. A package's line carries a curated description where its own says nothing, else the `.app` description. The platform is never listed, nor are exception structs. Docs are served from compiled artifacts: a defined module by its beam path, everything else by name, so a granted package is self-documenting. `Host.Repo` joins `Ecto.Repo`'s callback docs onto its generated functions, the one special case. A refused module or function gets the scanner's own copy, so a refused `print_docs` carries the same signage hint a refused call does. `print_source` serves defined and quarantined modules and nothing else. Migrations are not listed: `Host.Migrator.print_migrations/0` is their home and speaks in version numbers, and a web module carries no route suffix, since the URL surface is `Host.Router.print_routes/0`'s. A one-line footer after the libraries points at `print_docs`, `print_routes` and `print_migrations`, so the one print an agent is steered to names the other three.

**Tools and grants are independent.** The default grants `Host.Code` whole, so a policy with `tools: [:eval]` cannot define modules but can remove them. Kept, because coupling them would be the first place a tool implied a grant; a token that should not tear modules down gets `allow: [{Host.Code, except: [remove: 1]}]`, documented on `Beamlet.Policy`. Per-module ownership, alice's module that bob cannot remove, is deferred (§ 4).

### PubSub

Settled 2026-09-16. `Beamlet.PubSub` is the beamlet's message bus: one `Phoenix.PubSub` registered under that name as a child of `Beamlet`, and the name is the whole thing; a module for it was written and dropped, since nothing called it. The one line an embedder needs, `pubsub_server: Beamlet.PubSub` on their endpoint, is in the `Beamlet` moduledoc beside the child list. `Host.PubSub` is `subscribe`, `unsubscribe` and `broadcast` over it, with topics one shared namespace the moduledoc tells agents to prefix. `broadcast_from` waits for something to ask.

### Files

Settled 2026-09-16. `Host.File` is `File`, scoped to `<data_dir>/files`, the root `Beamlet.Config.files_dir/0` names and the boot creates. The name follows `Host.Repo` for `Ecto.Repo` and `Host.PubSub` for `Phoenix.PubSub`: the leaf name of the module it stands in for, so an agent's `File` priors are right rather than corrected by an index. The functions are `read`, `write` with modes, `ls`, `mkdir`, `mkdir_p`, `rm`, `rmdir`, `cp`, `cp_r`, `rename`, `exists?`, `dir?` and `regular?`, each returning what `File`'s does, `{:error, posix}` included, with a bang variant raising what `File`'s raises, `File.Error`, `File.CopyError` or `File.RenameError`, naming the path as the agent wrote it. All three are in the granted exception family, so a `rescue File.Error` written from priors works. `ls_r` is the one function `File` lacks: a recursive listing as sorted root-relative paths, the thing agents most often want. Two deviations from `File`, each documented once: writing, copying and renaming create the parent directories they need, saving an eval round trip, and `rm` answers `:eisdir` for a directory where `File.rm` says `:eperm`. Left out: `stat`, since `File.Stat` is denied and nothing asks for size or mtime yet; `rm_rf`, since on a shared root file-only removal bounds cross-user accidents; `cp`'s options, whose `on_conflict` callback would see host paths; `wildcard`.

Tuples and bangs both, not raise-only: the same module runs in controllers and LiveViews, where a missing file is a 404 to handle, not a 500. One shared root, stateless resolution that needs no principal and so works the same from an eval, a web request or a LiveView, a leading `/` meaning the root, every path containment-checked, error copy that never shows a host path, no git audit and no size caps. An escape or a non-string path raises `ArgumentError` from tuple and bang alike: misuse of the API, not a condition to handle. Containment is lexical through `Path.expand`; only an operator can plant a symlink under `files/`, and that is accepted rather than resolved on every call. One module, tested directly under `Beamlet.Case`, which wipes `files/` per test. The scanner expands aliases before its check, so `alias Host.File` lets agent code read exactly as `File` code: allowed and not advertised, since the visible `Host.` prefix is what tells a reader of `print_source` that the scoped door is in use.

### Key/value

Settled 2026-09-17. `Host.KV` is durable storage for small state under string keys: `fetch/1`, `get/2` with a default, `put/2`, `delete/1`, `all/1` and `keys/1` under a prefix with an empty prefix meaning everything, and `delete_all/1` under a prefix with no default so wiping everything is written deliberately. Values are any term, stored in external term format in the `__kv` table of the agent database, so a put inside a `Host.Repo.transaction` lands with the agent's own rows. Keys are one shared namespace the moduledoc tells agents to prefix, as with PubSub topics. `fetch/1` exists because a stored `nil` and a missing key are different answers and `get/2` cannot give both; `fetch!/1` does not, having no scenario. `Beamlet.KV.Entry` and `Beamlet.KV.Term` sit beneath the module as internals. A granted schema for agents to query the table through `Host.Repo` was declined: the value column is opaque to SQL, so the only key-shaped operations it would open are the ones the module already has, at the cost of pinning the table name and the encoding as public API.

### Migrations

Settled 2026-09-17. A migration is a plain `use Ecto.Migration` module through the define tool, recognised by the exported `__migration__/0` after the buffer compiles and filed under `code/migrations/NNNN_name.ex` with a version the beamlet assigns: one past both the files on disk and the versions the agent database records as applied, in buffer order, so a git rewind that removes an applied migration's file cannot see its number reused and the migration silently skipped. A replaced migration keeps its version and file; a replace that changes a module's kind moves its file between the roots. Define never applies: the summary line carries the pending cue. The pending rule: a migration is editable until it has run, and an applied one refuses replace and remove until rolled back, so the applied stack and the files never disagree. Boot compiles both roots in one batch and the audit commits both.

`Host.Migrator` holds the verbs, `migrate/0`, `rollback/0` and `print_migrations/0`, printing as they go and returning `:ok`, with `Ecto.Migrator.up/4` and `down/4` against `Host.Repo` one migration at a time so a mid-batch failure leaves the earlier ones applied and names the one that failed. `Beamlet.Migrations` is the history they and the code server share: the applied versions and the join of the manifest with Ecto's own `schema_migrations` table. An applied version whose module is gone is an orphan, which only an operator can make since the pending rule stops an agent: the version floor counts it, the listing marks it as applied with its source missing, and rollback refuses past it with a teaching error, because Ecto would otherwise undo the migration beneath. The sweep log surfaces the hand edit that caused it.

### Config

One surface: `:beamlet` application config, read at runtime through `Beamlet.Config` accessors, so a release or container sets it from the environment in `runtime.exs`. No start options carry configuration, nothing is read at compile time, nothing is stashed. Checked once, read plainly after: `Beamlet.Config.validate!/0` checks every key first thing in `Beamlet.init/1`, on both boot paths, and fails the boot naming the key at fault; the accessors then return what was checked with defaults merged and never raise. Validating in each accessor lost: it spread the boot's job across every caller and made runtime paths look fallible when a change is a restart. `data_dir` is the root everything a beamlet persists lives under; starting checks the dir exists and fails the boot otherwise, and the modules owning paths beneath it add their accessors as they arrive: `db/`, `code/` and `files/`. The web surface is the `web` group, `endpoint` and `prefix`: the full boot fails without an endpoint, since the routes are served through it, and the system half needs none. Tests use one data dir per run, `tmp/test_data` in the repo, wiped at the start of each run; a test that needs its own directory gives it to the component directly rather than through config. The one surface has a second source in a container: a release merges an optional operator config file, `<data_dir>/config.exs`, into it through `Beamlet.Config.Provider` (§ Deployment). Mix runs no config providers, so in development each project's `dev.exs` imports the same file from the shared dev data dir when it exists, and a dev policy is declared once rather than in both projects.

### MCP

`Beamlet.MCP.Server` (Anubis, Streamable HTTP) runs as a child of `Beamlet` and serves two tools, `define` and `eval`. Unprefixed: the protocol makes names unique per server and clients namespace across servers themselves (Claude Code shows `mcp__beamlet__eval`), so a `code_` prefix would only repeat the server name. `eval` rather than `exec` because the tool evaluates an expression and returns its result, which is what Elixir calls it. Schemas carry only what the tool needs; there is no per-call description field, since the client owns its UI and already shows the arguments. A host serves the tools by forwarding to `Beamlet.Router`, which mounts `Beamlet.MCP.Plug` at `/beamlet/mcp`, under the beamlet's reserved segment.

Server instructions and each tool description are held under 2,048 bytes by tests: Claude Code truncates both at 2KB, and bytes are the conservative measure against a client counting characters. The instructions are a pointer block, what matters most first and the stdlib for the rest.

**Where context lives** (2026-09-18). Instructions and descriptions land in every session of every user who has the server configured, including sessions that never touch the beamlet, so the static footprint is kept well under the cap rather than at it: the instructions around 1.4KB, `define` around 1.2KB, `eval` around 0.7KB, editorial targets the tests do not pin. The spike licensed that: clients cut at 2KB did the work as well as one that delivered the whole 15KB block, so the descriptions and the teaching errors carry what matters at call time and the instructions mostly buy polish. Context sits on a ladder, and a piece goes on the lowest rung that still reaches the model in time. The **instructions** carry what a model needs before its first tool use: what a beamlet is, the tools in a sentence each, the first calls to make, and the five slips the spike saw models make (fresh bindings per eval, `print_*` prints and returns `:ok` and several fit in one eval, `import Ecto.Query`, the beamlet is shared so read first, verify with `Host.Router.call` before reporting done). They are static per server, so they speak of `eval` throughout and of `define` as "when it is in your tool list", which is how they survive an eval-only token. A **description** is that tool's call-time contract, with the configured limits interpolated: for `eval` the empty bindings, the output shape and cap, "end with `:ok`", the timeout; for `define` the buffer rules, reserved names, the docs gate with its framework exemption, what `replace` does to dependents and mounted routes, migrations filed pending. A **moduledoc** carries the conventions of one module, served by `print_docs`: `~H` templates, `~p` inside them, `<.link navigate>` against a plain anchor, the layout and Tailwind, and live updates through PubSub on `Host.Web`; the query import, `:map` keys as strings and one statement per `query!` on `Host.Repo`; the rollback-replace-migrate loop and SQLite's column-change recipe on `Host.Migrator`; replace-not-remount on `Host.Router`. A **teaching error** carries the correction at the moment of the slip, and a **print** carries state, never conventions. Neither `print_environment` nor a page-per-topic wiki earned a place: the listing's footer names the other prints, and every convention had a module to own it (§ 4, virtual paths).

**The `eval` description is the floor** (2026-09-20). The claude.ai app drops server instructions entirely (anthropics/claude-ai-mcp#93), and in a tool-rich session shows about eighty characters of each description until the model loads the tool; the same connector in Claude Code delivers the instructions whole, so support is per client and cannot be assumed. What reaches every client is, in order, the first sentence of each description, the full description once loaded, and tool results. So the ladder's top rung is a bonus, not the floor: each description opens with one sentence under eighty characters saying what the tool is for, and the `eval` description, the tool a model loads first, carries the orientation and the slips as well, at about 1.4KB, with the instructions kept whole beside it and the duplication accepted for clients that show both. The teaching errors carry the discovery pointers a blind model needs: a guessed `Host.*` name is sent to `Host.Code.print_modules()` rather than told to define it first, and the `Code`, `:code` and `Module` refusal names the listing beside the define tool, since the first thing a model with no instructions does is probe for what exists. A help tool and a `Host.help/0` were declined: a third tool costs every session on every client, and the guess it would answer is caught by the refusal at no cost.

**The first paragraph is the listing.** `print_modules` and the function index in `print_docs` render the first paragraph of a `Host.*` moduledoc and `@doc`, ExDoc's summary convention, so on a Host module that paragraph is one short sentence and the explanation starts in the second. Library and framework modules keep their own conventions and are listed by name alone.

### Login and OAuth

Settled 2026-09-21 in four phases, verified against clients 2026-09-22, the pages made LiveViews 2026-09-23.

**Why both a header and a browser flow.** ChatGPT connects a custom server by OAuth or not at all and says outright that it cannot present an API key; claude.ai offers an individual OAuth or nothing; Claude Code takes either; code takes a header only, since a server-side loop has no browser to complete a redirect. So the hosted chat clients need OAuth and the audience's own agents need a header token, and both stay. Rejected: a token in the URL path, which lands in every request log and is still a secret pasted into a third-party app, the thing OAuth removes; a stdio proxy on the user's machine, which reaches only clients that spawn local processes; a hosted authorization server such as Clerk, Auth0 or WorkOS, which would remove the issuing half at the cost of a third-party identity account as a runtime dependency of a self-hosted server, policy on the user because a provider's consent screen offers no choice, and an internet connection for local development, kept in view since Beamlet's resource-server side is issuer-agnostic and could later point at an external issuer; and the Elixir libraries, none of which fit a SQLite-backed single-tenant server issuing opaque tokens (`boruta` is Postgres and beta, `ex_oauth2_provider` has no PKCE, the rest are JWT-only or need Ash). The issuing half is a login, two endpoints, a consent page, a code store and a client-document fetch, and rolling it was a couple of days.

**Vocabulary.** The **client** is the app connecting and identifies itself by a **client id**. Beamlet plays both OAuth roles at one origin: the **resource server**, the MCP endpoint, and the **authorization server**, which issues tokens. **Protected resource metadata** (RFC 9728) names the authorization server; **authorization server metadata** (RFC 8414) names its endpoints and what it supports. A **client ID metadata document** (CIMD) is how a client registers without registering: its id is an https URL on its own domain serving a JSON document with its name and redirect URIs; **dynamic client registration** (RFC 7591), an unauthenticated endpoint storing clients in a table, is the older alternative the 2026-07-28 MCP revision deprecates. **PKCE** binds an authorization to the client that started it: a hash of a secret when asking, the secret itself when redeeming. An **authorization code** is the short-lived, single-use string the browser carries back after consent, worthless without the PKCE secret. The **access token** rides in the bearer header; the **refresh token** is redeemed for a new pair; **rotation** means a refresh token dies the moment it is used. The **resource** parameter (RFC 8707) names the MCP URL a token is for.

**Beamlet's own plug plays both roles; Anubis is the transport.** `Beamlet.MCP.Plug` wraps the transport plug with the server baked in, so `Beamlet.Router` mounts it with one forward. It runs on every request and method: reads the `Bearer` secret, authenticates it through `Beamlet.Users`, and puts the principal in the conn's assigns before forwarding; Anubis re-merges the conn's assigns into the frame on every message, so `frame.assigns.principal` in a callback is always the current request's, which is what makes identity per request rather than per session. A missing token, another scheme, an unknown secret or an `oauth` token past its expiry is a 401 whose `Bearer` challenge carries the realm `beamlet` and the `resource_metadata` URL, which is how a chat client discovers that this beamlet is its own authorization server; a token naming a policy the beamlet no longer declares, or one outside its user's list, is a 403 with a line naming both. Anubis's own authorization was weighed twice and lost twice: it would have needed a wrapper plug anyway for the transport's compile-time `request_timeout`, the public URL at server start, a guard for task-style tool calls whose frame carries no claims, and an idle Finch pool, and a validator failure is always a 401, so the 403 would go; matching what it does is one header parameter and one expiry clause. `Beamlet.OAuth` holds the shared facts, the issuer, the resource `/beamlet/mcp` and the two discovery documents, built at request time from the endpoint's `url` config, so the public URL is not a config key and is never needed at boot; `Beamlet.OAuth.MetadataController` serves the documents at the root (§ 2 Web).

**Login.** A user has a nullable `password_hash`; `users.create` prompts for a password unless `--no-password` says the user will not sign in, which is all a user whose only credentials are tokens needs; `users.update --password` sets or resets one, and `users` shows who can sign in. The password is prompted for, never an argument, so it stays out of the shell history. Under `-noshell`, which is how `mix`, `elixir -e` and a release's `eval` all run, `:io.get_password/0` answers `enotsup`, so the CLI switches to OTP 28's raw no-shell mode for the read alone (`:shell.start_interactive({:noshell, :raw})`) and back after, since output printed while raw loses its carriage returns; when stdin is a pipe the read is a plain line. Hashing is `pbkdf2_elixir`: pure Elixir so the image needs no native build, the modular crypt format so the row is one string, a dummy verify so an unknown name costs the same as a wrong password, and a rounds setting the test config drops to one; `Plug.Crypto`'s key generator lost on having to write the salt, count, encoding and compare ourselves. Eight to 128 characters and no other rule. The session is the host's cookie session holding the user's id and nothing else; every request loads the user again, so a rename holds and a deletion signs out. `Beamlet.Web.Auth` is the whole of it: `fetch_current_user` and `require_auth` as plugs, the latter storing a GET's path to return to, `on_mount` hooks of the same two names for a `live_session`, and `log_in` and `log_out`, which renew the session. The form is `Beamlet.Web.SessionLive`; it posts to `Beamlet.Web.SessionController`, which owns `/beamlet/logout` too, lands a sign-in on the stored path or `/beamlet`, and sends a failure back to the form with a flash. Accepted for 0.1, revisited at the security read (roadmap 0.1 step 11): a login lasts until sign-out or the browser drops the cookie, a password reset ends no other browser's session since a cookie session keeps no server state, and the login page does not rate-limit.

**Client identity: metadata documents only.** No dynamic registration, no clients table, no unauthenticated write endpoint; the fallback is added the day a client proves it needs it. The metadata advertises `client_id_metadata_document_supported` and `none` as the token endpoint auth method, the pair claude.ai requires before it chooses CIMD. `Beamlet.OAuth.Clients` fetches the https URL a client gives as its id, requires the document's own `client_id` to equal it and a non-empty `redirect_uris`, reads nothing else, not even the display name, and caches it for an hour. A redirect URI must equal a listed one exactly, except that a listed loopback URI matches either loopback host on any port (RFC 8252 § 7.3), which is what Claude Code sends. The fetch is guarded by `req_ssrf`: https only, no address literals, every resolved address checked, a failed lookup refused, plus no redirects, five seconds and 64KB of the beamlet's own; it won over hand-rolled code and over `safeurl`, which is IPv4-only and passes a failed lookup, and it offers the resolver seam the tests need. The DNS rebinding window stays open, as the library documents, since pinning the connection to the checked address costs a Finch instance per hostname; login comes before the fetch, so only a signed-in person can make the beamlet issue a request at all. The test seam is `config :beamlet, Beamlet.OAuth.Clients, req_options: [...]`, empty in production, carrying the `Req.Test` plug and a resolver in test; a `Beamlet.Config` key lost on putting a test seam on the operator surface.

**The flow, endpoint by endpoint.**

1. **Discovery.** A client calls `/beamlet/mcp` with no token and gets the 401 naming the protected resource metadata URL. That document names this origin as the authorization server; the authorization server document at `/.well-known/oauth-authorization-server` names the two endpoints below and declares S256, the code and refresh grants, `none` auth, CIMD support and `iss` support.
2. **Authorize.** `GET /beamlet/authorize` with `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method=S256` and optionally `resource` and `scope`. A signed-out person goes to the login and returns to the same request, query string included. An unknown client or an unlisted redirect URI is an error page, since the beamlet cannot safely redirect; every other fault redirects to the client with `error`, `error_description`, `state` and `iss`. `resource` must equal the MCP URL when sent.
3. **Consent.** The person chooses a policy and allows or denies; a code is stored and the browser goes back to the client with `code`, `state` and `iss`, or with `access_denied`.
4. **Exchange.** `POST /beamlet/token`, form-encoded, no session and no CSRF check since clients post directly, `grant_type=authorization_code`. The code is looked up and deleted, the client id, redirect URI and `resource` checked against what it was issued for, the SHA-256 of `code_verifier` against the stored challenge, and `Users.create_token` mints with the consented policy. The JSON reply carries the access token, `token_type`, `expires_in` and the refresh token; errors are OAuth error bodies, `invalid_grant` and friends, because the client reads them.
5. **Refresh.** Same endpoint, `grant_type=refresh_token`: look up the refresh hash, check its expiry, rotate in place, reply with the new pair. A used, expired or `cli` token is `invalid_grant`.

`Beamlet.OAuth.Codes` is the store between consent and exchange: a GenServer holding pending codes with the user, policy, client id, redirect URI, challenge, resource and scope, ten minutes, single use, swept every minute, gone at a restart, which means `invalid_grant` and the person connects again.

**The consent page** is `Beamlet.OAuth.AuthorizeLive`, behind the login. The request is validated at mount and held in the page's state, the decision is an event, so the form carries no hidden fields and nothing to validate twice, and the consent, error and sent states are renders of one module; the error page answers 200, since a LiveView sets no status and no client reads that page. It names the client by its id's host and never shows the document's display name, lists the policies the user may carry with their tools, `default` selected when on offer, has a Deny, warns when the redirect is loopback, and shows who is signed in. The way back depends on the redirect URI: http and https are a plain redirect, and a custom scheme, which is how a desktop app such as Raycast receives its code, renders a page with a meta refresh that sends the browser on and says the app has opened and the tab can be closed, since a redirect there opens the app and leaves the tab on the consent form.

**Lifetimes and scopes.** An access token lives a day and a refresh token thirty days, sliding: `Beamlet.Users.rotate_token/2` sets both from now and replaces both secrets on the same row, so a client in regular use never asks the person to consent again and the token id survives. Constants on `Beamlet.OAuth`, not config: revocation is delete, so a short access token would buy little. A row whose refresh has expired stays until the operator deletes it, and `beamlet tokens` shows the expiry. No scopes: none advertised, none understood, whatever the client sends is echoed in the token reply, which under RFC 6749 states what omitting it already implies. Claude Code requests the scopes the protected resource document lists and works without any; ChatGPT requests every scope the authorization server document lists and expects an exact echo; so listing none is what makes the consent page's policy choice the whole story. A one-scope or per-tool scheme lost: a scope that cannot be declined is decorative, and per-tool scopes would put a second permission axis beside the policy. No CORS and no dynamic registration until a client proves it needs them.

**Verified 2026-09-22** over a Tailscale funnel with every client on its defaults: ChatGPT connects and signs in smoothly; the Claude app's "use Claude's published identity" (CIMD) works, bouncing through a claude.ai page before the beamlet's consent; Raycast reaches for the metadata document and connects, and its custom-scheme redirect is why the sent page exists; the MCP Inspector detects the challenge but cannot run the flow itself, so it neither needed CORS nor proved it does. No client asked for registration and none tripped on the scope echo. Since the pages became LiveViews the flow has had a brief pass only; the four clients want another.

### Web

Settled 2026-09-17. The pages and APIs agents build are served by the host's own endpoint, named in config, and Beamlet owns the router that serves them, the layout they render in, and a plain error view.

**The host forwards at the root, last.** The one line a host writes is `forward "/", Beamlet.Router` as the last route of its router. Last because a root forward matches everything after it, so host routes win by order. At the root because LiveView's connected mount re-matches the full browser URL against the router that dispatched the page, stripping only the endpoint's script name, and `Phoenix.Router.route_info/4` never recurses through a forward; a forward at a prefix therefore breaks every LiveView page.

**Root by default, and a reserved namespace.** No prefix: "add a dashboard to my beamlet" is served at `/dashboard`. The beamlet owns every path whose first segment is `beamlet`: `/beamlet/mcp` for the MCP server, `/beamlet/live` for the LiveView socket, `/beamlet/assets/...` for the JavaScript and the stylesheet, `/beamlet/login` and `/beamlet/logout` for the sign-in, `/beamlet/authorize` and `/beamlet/token` for OAuth, `/beamlet` for the home page and later the admin pages; a first segment of `beamlet` is refused at mount. One named segment rather than an underscore marker (2026-09-21): a marker suited paths no person types, and once the beamlet had pages for a browser, `/_/login` read as a mistake where `/beamlet/login` reads as what it is. The cost is that an agent cannot mount `/beamlet`, a page nobody was going to build. A leading `~` is reserved the same way, for the per-user scope § 4 keeps open, and costs nothing now. The prefix survives as an embedder's option, `config :beamlet, web: [prefix: "/app"]`, for a host that wants agent-built pages fenced under its own namespace; the generated router bakes it into its scopes, since a forward cannot supply it. The beamlet's own paths never take the prefix. The one beamlet-owned surface outside the segment is the pair of OAuth discovery documents, which the specs fix at `/.well-known/oauth-protected-resource`, also served with `/beamlet/mcp` appended since clients try that form first, and `/.well-known/oauth-authorization-server`: three exact routes in `Beamlet.Router` ahead of the forward. `.well-known` is not a reserved segment, since an agent may have its own use for the directory; the three paths win by order.

**Two routers.** `Beamlet.Router` is static and public: it carries the beamlet's own routes under `/beamlet`, the MCP plug, the sign-in and the home page, and forwards everything else to `Beamlet.DynamicRouter`, so the beamlet decides what lives under `/beamlet` and the host's line never changes. Because it sits behind a root forward, it carries LiveViews directly, with no router macro. `Beamlet.DynamicRouter` is the generated module: a compiled-in empty placeholder, so the forward compiles, that `Beamlet.Routes.regenerate/0` replaces in the VM by rendering the route table into a real `Phoenix.Router` source (`Beamlet.Routes.Generator`, internal) and compiling it through `Beamlet.Code.compile_artifact/2`. A derived artifact: never on disk, never committed, rebuilt from the table at boot and after every change. Two convention pipelines, LiveView rows through a browser pipeline with session, CSRF protection and the root layout, controller rows through an API pipeline with neither so a webhook can call them; no plug kind, no per-mount override. Rows render in mount order, so an earlier mount wins an overlapping match as in a hand-written router. Folding the static routes into the generated source lost: it couples the MCP mount to an artifact that fails and rolls back.

**The table.** `Beamlet.Routes` is the context over `__routes` in the agent database, with `Beamlet.Route` at the root beside it: kind, verb, path, module in inspect form, an optional action, the principal as JSON and `inserted_at`, unique on verb and path with a LiveView storing `get`. The format validations are load-bearing, since the fields interpolate into router source. `create`, `delete` and `list` change or read the table and nothing else; regeneration is the caller's to compose, which `Host.Router` does by inserting, regenerating and deleting the row again when regeneration fails. A row whose target is missing, quarantined or of the wrong shape is left out at generation with a warning and answers 404; the row stays for inspection, and `servable?/1` is the one rule discovery and remove share. The boot child is synchronous, right after the code server, returns `:ignore` and never fails the boot: the worst case is the placeholder serving 404s with an error in the log. An empty table and an empty loaded router already agree, so boot compiles nothing in that case, which is what keeps a suite that boots a beamlet per test from paying a forty-millisecond router compile each time.

**What the host carries** is written down twice: as the list of integration points on `Beamlet.Router` and as `Beamlet.TestEndpoint` in the library's test support, which `Beamlet.Case` starts after every beamlet and the server app copies. In the router, the root forward; in the endpoint, the session, the LiveView socket at `/beamlet/live`, `Beamlet.Assets` and the JSON and urlencoded parsers, the latter for the sign-in form and the token endpoint; in config, the endpoint named under `:web`, `pubsub_server: Beamlet.PubSub` and `render_errors`. `Beamlet.Assets` is a `Plug.Builder` over three `Plug.Static` plugs under `/beamlet/assets`: the LiveView JavaScript from the deps' precompiled bundles, so there is no JavaScript build, and the beamlet's own stylesheet from the package's `priv/static`; it is a plug on the host's endpoint rather than a forward inside `Beamlet.Router` because agent-installed JavaScript (§ 4) may grow it and how it is consumed is reviewed then. The web pieces live under `Beamlet.Web`. `Beamlet.Web.Layouts` holds two root layouts: `root` is the agent pages', CSRF token, the two modules, the socket, Tailwind from its CDN, and nothing about how a page looks, styling needing the internet being accepted for a substrate with no bundler; `beamlet` is the beamlet's own pages' root, the same wiring with the built stylesheet in place of the CDN. Inside it, `split/1` is the layout for the sign-in and consent pages, the panel with the wordmark, a tagline and the beamlet's address beside the form, and `app/1` the signed-in pages', the top bar with the host, the signed-in name and the sign-out. `Beamlet.Web.ErrorView` renders a status message as text or as JSON, so a miss under the forward is a plain 404 and the test endpoint and the server need no error view of their own; the HTML 404 adds one sentence saying the beamlet has its own pages at `/beamlet`, since `/` is a miss until an agent mounts it. A host with its own error view keeps it.

**The beamlet's own pages are styled by a built stylesheet** (2026-09-22). The sign-in, the consent page and the home page are the beamlet's, so they need no build step of the host's: the `tailwind` hex package, a standalone binary with no Node, builds `assets/css/beamlet.css` into `priv/static/beamlet.css`, Tailwind v4 scanning `lib/beamlet` for classes, and the output is committed, as `phoenix_live_dashboard` ships its stylesheet, so the hex package, a git dependency and the Docker image all carry it with no extra step. `mix assets.build` refreshes it and `precommit` runs that beside `format`, so the file cannot drift; the dependency is dev and test only, never runtime. The server's dev config has one watcher, which runs the library's mix task in the library directory with `--watch`, so one config owns the build. Development reloads the library as well as the server: the endpoint names `:beamlet` among its `reloadable_apps`, so a request recompiles a changed template, and `phoenix_live_reload` watches the library's directory beside the server's, set by absolute path in `config :phoenix_live_reload, :dirs` since its default is the server's root alone; a stylesheet change swaps in place and a template change reloads the page. The pattern for new views is a Claude Design mockup, an implementation from it, then hand refinement against the live page. No JavaScript pipeline: an entrypoint and esbuild were weighed and put off until a page needs a hook, likely the admin pages, since without colocated hooks a bundle would carry nothing the raw modules do not. Agent pages keep the CDN and the raw modules.

**The design language is the design system's tokens, not its components** (2026-09-22). The Beamlet design system lives in Claude Design, far larger than the pages need, and the codebase takes from it in the order a page asks. `assets/css/beamlet.css` carries a Tailwind `@theme` that replaces Tailwind's palette with the putty, slate, rust, phosphor and ochre ramps and names roles over them (page, card, strong, body, muted, faint, link, primary, danger, hairline, line), plus the three fonts, the type scale, the radii, the hard offset shadows and the fast easing, and a base layer for the page ground, headings, links, inline code and the focus ring. Replacing the palette is the point: a page can only name colours the language has, so drift shows as a class that styles nothing. The fonts load from Google Fonts with system fallbacks, as the CDN already does for agent pages; packaging them is open. `Beamlet.Web.Components` holds a piece once a second page needs it: wordmark, button, input, flash, code panel and numbered steps so far. Icons stayed out.

**Every view is a LiveView** (2026-09-23). A template lives in a render function or a function component and nowhere else: no static `.heex` files, no `_html` view modules, one way HEEx works across the beamlet's pages, and the admin pages to come are LiveViews anyway. What is not a view stays a controller: the session writes in `Beamlet.Web.SessionController`, the token endpoint and the metadata documents. The sign-in LiveView renders the form and posts it to the controller, as `phx.gen.auth` does, because a session cookie is written on an HTTP response. The consent LiveView holds the request in its state and takes the decision as an event. Accepted: the consent page needs the socket up before Allow does anything, which the long-poll fallback covers; every client tested opens the page in the person's default browser, not an embedded one.

**The home page** (2026-09-22) is the setup page at `/beamlet`, behind the login: the MCP URL with a copy button, then one client at a time under tabs chosen by the `client` query parameter, so a tab has a URL. Apps, Claude and ChatGPT by name and any other OAuth client, connect by signing in on the consent page. Coding agents that offer OAuth sign in from the terminal with their own commands. Everything else, Cursor, a project's `.mcp.json` and code calling the Claude or OpenAI API, sends a `cli` token in a header, and the page shows the `beamlet tokens.create` command with the signed-in name filled in for the operator to run. The rule is OAuth where a client offers it and the header everywhere else. The page mints nothing and lists nothing: self-service tokens and the token list wait for the admin pages in 0.5, and management stays operator-only. No plan or pricing claims, since which plans can add connectors changes without notice; the page gives the menu path and the form fields as of writing. `mcp-remote` for stdio-only clients is off the page until someone cannot connect without it. Copy on these pages is reviewed by a human read, not pinned by tests; a view test asserts on structure and behaviour.

**The agent face** is `Host.Web` and `Host.Router`. `use Host.Web, :live_view | :controller | :live_component | :html` is the one `use` line an agent writes; it brings the framework for the role, `Phoenix.HTML`, the `JS` alias and `~p`, and an unknown role is a teaching error at define time. `Host.Router` holds the verbs, `live/3` and the five named for HTTP verbs, `unmount/2`, `path/1`, `url/1`, `~p`, `call/4` and `print_routes/0`. Two words kept apart: a *path* is what the agent chooses and every function takes, never carrying the operator's prefix, and a *URL* is what people are given; `path/1` and `~p` map the one to the browser path and `url/1` to the other, and a path that already carries the prefix is refused with the relative form suggested, only when a prefix is set. A mount validates the path (a string, a leading slash, the row's format), refuses a reserved first segment with copy naming the convention, requires the target to be in the code server's manifest and of the right shape (`__live__/0`, or `action/2` plus the action), then composes `Beamlet.Routes`: insert, regenerate, delete the row if the router failed to build. Mount and unmount require the ambient principal and the row records it; a conflict names the mounted route and the user who mounted it. `print_routes` prints the base once, then verb, path, target, mounting user, and a not-served annotation from `servable?/1`.

`call/4` is a real request through the configured endpoint over `Plug.Test` in the calling process, the response returned as data with JSON decoded, the adapter's mailbox messages drained so they never reach a LiveView's `handle_info`, and a crash re-raised with the route's frames above the endpoint. It sets the ambient principal aside for the dispatch and restores it after (`Beamlet.Principal.delete_current/0`), so a route behaves under `call/4` exactly as it does in a browser: a served route acts as nobody, and a controller action that reaches for `Host.Code` or the mutating verbs raises either way. Without that, an agent's test call would pass where a visitor's request fails.

**Every dynamic route is public.** The login guards the beamlet's own pages, never an agent's; private routes stay open in § 4.

### Deployment

Settled 2026-09-18: a release in a Docker image, with the operator config file still to come (roadmap 0.1 step 6). The server app is endpoint, application module and config under one `BeamletServer` namespace, no tests of its own. The image is multi-stage on the hexpm Debian builder and the matching slim runner, since the release carries ERTS and the SQLite NIF built against the builder's libc; the runner adds git, which the code audit shells out to, and runs as the `beamlet` user, uid 1000. The release keeps the Docs chunk (`strip_beams: [keep: ["Docs"]]`), since `print_docs` and the policy's `@moduledoc false` filter read it, and always serves: no `PHX_SERVER` toggle. The operator surface is three variables and a volume: `BEAMLET_DATA_DIR`, `/data` in the image, holds everything including the cookie secret, generated on first boot into `secret_key_base` when `SECRET_KEY_BASE` is unset; `BEAMLET_URL`, one variable for host, port and scheme, which LiveView's origin check and the OAuth issuer key on; `PORT`. TLS is the proxy's: `force_ssl` is compile-time config and would break plain HTTP on a LAN, so it is out, and `Plug.RewriteOn` reads the forwarded scheme so the session cookie is marked secure behind the proxy. `bin/beamlet` is an overlay script over the release's `eval`, which passes trailing arguments to `System.argv/0`, runs the config providers and loads the release without starting it; the CLI starts the system half itself, so the script works on a fresh volume and beside a running server. `fly.toml` at the root is one machine in one region with the volume at `/data` and auto-stop off, since a beamlet's modules are compiled into the running VM. The library's only declaration surface is application config, so the release merges an optional operator config file, `<data_dir>/config.exs`, into it at boot through `Beamlet.Config.Provider` (settled 2026-09-23): a plain `import Config` file, one file with imports disabled, read after `runtime.exs` and merged over it, so the file is the last word; absent means nothing, silently; one that fails to evaluate fails the boot naming the file and the line, which the provider takes from the compiler's diagnostics since Elixir reports an undefined name as a line-zero error. The file is for the beamlet's own keys, the policies above all, but it is ordinary application config and can set any key of any application, the environment's included; the docs say that is not the intended use rather than the code preventing it. The stance: the environment configures the deployment, the file configures the beamlet, and wanting more is wanting a different host, which is the child spec in your own application. Restricting the file to `:beamlet` was weighed and dropped as a rule for nothing. The release's `eval` runs the providers, so `beamlet policies` in the container reads the file afresh and is the check, before any restart. The operator loop is the same on Docker and Fly: write the file locally, put it on the volume (`docker cp` into the container, whether running or stopped; `put` in `fly sftp shell`), run `beamlet policies`, restart, create the token with `--policy`. The image has no editor, and the file must stay readable by uid 1000, which `docker cp` preserves from the local mode.

## 4. Deferred

- Admin UI. The admin LiveViews sit in `Beamlet.Router` under `/beamlet`, beside the home page and behind the login (roadmap 0.5).
- Private routes. A private route keys on the web identity for access and on the row's provenance for ownership, never on the principal (§ 2 Users, tokens and principals). Two shapes were weighed and neither chosen: a property of the route, `private: true` on the mount, keeping one namespace with the generated router putting the row in a scope that requires a login; or a per-user scope in the path, `/~alice/notes`, mirroring `~home/` below and nesting under any prefix. The reserved leading `~` keeps the second open, and the path-to-browser-path indirection `Host.Router` carries (`path/1`, `~p`) is the seam either would fill.
- A principal handed in by an embedding host calling tools in-process, without a Beamlet token. If it returns, a principal that encodes and decodes is the seam.
- User-scoped modules, routes, files and KV entries beside the shared ones, and with them per-module ownership, so that alice's module is not bob's to remove. The user id on every principal is what it would key on. A private file area would be a `~home/` mount on `Host.File` (next item), eval-only, since a served route has no principal to be.
- Virtual paths on `Host.File`: a `~name/` prefix, which cannot collide with an agent's directories and which `Path.expand` leaves alone, resolved through a mount table from prefix to directory and mode; a read-only mount refuses writes with a teaching error and lists beside ordinary entries. The first candidate is `~docs/` over the package's `priv/docs`, documentation for agents served as read-only files, each page under eval's output cap. Kept deferred because every convention so far found a module to own it, and a wiki with three pages is a second discovery surface the instructions would have to spend bytes pointing at. The trigger is a topic with no owning module, an end-to-end tutorial or operator notes, or a Host moduledoc outgrowing about 4KB. MCP resources are the other shape for documentation and lost to the rule that everything is reachable through `eval`.
- Supervised processes for agent code (roadmap 0.2).
- Agent-installed dependencies, and with them who grants an installed package to agent code (roadmap 0.6).
- Package-level denial in a policy (`deny_app`) and reloading policies without a restart, each when a policy needs it.
- Static assets, and agent-installed JavaScript and CSS, with colocated JS and CSS in agent modules as the likely shape (roadmap 0.3). `Beamlet.Assets` is where served files would grow. Colocated CSS needs `config :phoenix_live_view, root_tag_attribute:` set in the VM that compiles the module, which for agent modules is the beamlet's, so the setting is the library's to make or require of every host, not the server's; and both extract to files under `_build` that a bundler is expected to pick up, which the no-bundler substrate would have to serve itself.
- A hosted or external OAuth issuer in place of Beamlet's own, which the issuer-agnostic edge allows.
- The modern-era MCP protocol (2026-07-28); Anubis 2.0 is legacy-era and current clients negotiate it.
- Any dependency on Omni packages. If `omni` is ever added, it is as a library for agents to use, not as a foundation.
