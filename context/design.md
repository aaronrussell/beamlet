# Beamlet — design

**Status:** Working note, deliberately light. It records what is settled and why, one decision at a time as the code lands. Nothing is carried over from `../omni_host` unexamined. History lives in git; this note keeps the decisions and the reasons that still bear on the next one, and an alternative only where someone would plausibly propose it again.

**Last updated:** 2026-10-01 (policies as guardrails, not containment; private routes as owner-only; the threat model moved to `security.md`)

---

## 1. Framing

**Name:** Beamlet. **Package:** `beamlet`.

*A little Elixir server to make your own.*

Beamlet is a programmable Elixir code server for AI agents. Agents can define modules, execute code, and build APIs and live dashboards inside a running application. Available as an embeddable Elixir package and a standalone MCP server, independently of Omni.

A small, persistent computing environment to tinker with, not a disposable code runner. Primarily for Elixir developers having fun building things with agents, rather than an enterprise automation platform. The tone is friendly, curious and technically fluent: playful without being childish, concrete rather than full of AI hype.

### Language

- **Beamlet** is the project.
- **A beamlet** is a running instance.
- **My beamlet** is where your code and applications live.

The name works in prompts: "What routes exist on my beamlet?" "Add a dashboard to my beamlet." The agent works *on* your beamlet; it is not the beamlet. Different agents and clients interact with the same environment.

"A beamlet" is the only new noun. Everything else stays ordinary: modules, routes, tools, applications, users, tokens.

### Why the name

Short, memorable, connected to the BEAM. The diminutive suggests something approachable and personal, a little computer you can make your own. It names the thing itself without "server" or "instance" appended.

## 2. Settled

Each entry is a starting position, held until the code says otherwise, dated when it was settled.

### One package, one nested server

```
beamlet/                 the repo and the hex package
  lib/host/              Host.*          agent-facing stdlib
  lib/beamlet/           Beamlet.*       machinery, databases, owner and tokens, web pieces
  lib/beamlet/mcp/       Beamlet.MCP.*   Anubis server and tool components
  server/                beamlet_server  the standalone Phoenix app, path dep on `..`
  Dockerfile             builds and runs the server
  fly.toml               one machine, one volume, for the image on Fly
```

The library is a **child spec** a host starts in its own supervision tree; it declares no OTP application of its own. This keeps boot ordering in the host's hands, lets tests start and stop a beamlet per test, and makes the standalone server the smallest possible consumer rather than a special case. `start_link/1` takes `only: :system` to start the policies and the system database alone, migrated, which is what the operator CLI needs in a VM with no beamlet running; the knowledge of a beamlet's processes stays in `Beamlet.init/1`.

The server test: `server/` holds nothing a second embedder would want. Endpoint, application module, config, release, Dockerfile. Anything else belongs in the library, the admin UI included, which ships as LiveViews in `Beamlet.Router`.

### Two surfaces

`Host.*` is what agent code reads and calls. `Beamlet.*` is what the operator and the embedding host use. The name `Host` is kept from code mode on purpose: it reads well ("the host of my code") and agent-facing vocabulary is the most expensive thing to rename once it lives in docs, teaching errors and model habits.

**Where the machinery behind a `Host` module lives** (2026-09-16). `Host.X` is the agent surface: it prints, raises with teaching copy, returns plain values, and is granted wholesale by the policy, so it holds only what an agent may call. The implementation sits in a root-level `Beamlet.*` module only when it earns its place: something else in Beamlet calls it, or it is a real subsystem, a context over a table, a process, a generator. Otherwise `Host.X` is the whole thing. The two sides share a leaf name when they are the same thing seen from each side (`Beamlet.Code` and `Host.Code`, `Beamlet.Repo` and `Host.Repo`), and a table follows the context convention (`Beamlet.Routes` owning `Beamlet.Route`, with `Host.Router` as the agent face). A support module has a moduledoc when an embedder might call it and `@moduledoc false` otherwise. Nesting the implementation inside the `Host` module lost: it puts machinery in the agent's territory, where the listing, the reserved-prefix check and the moduledoc rule would all need a special case. Nothing under `Beamlet.*` is granted, so the split is what keeps the machinery out of reach by construction.

**Where a schema sits** (2026-09-17). A schema that is a resource of a public context sits at the root beside it, singular: `Beamlet.Token` beside `Beamlet.Tokens`, `Beamlet.Route` beside `Beamlet.Routes`. A schema that is a private detail behind a `Host` module with no context nests under that module's internal namespace with `@moduledoc false`: `Beamlet.KV.Entry` is the encoding of `Host.KV`'s rows and nothing outside the module touches it. One rule, applied to a public resource and to an implementation detail.

### Two databases

Both Beamlet's, both under the data dir:

- **Agent database** (`Host.Repo`): tables agents migrate and query, the key/value table, and the route table. Everything an agent builds, so it wipes and backs up as one unit.
- **System database** (`Beamlet.Repo`): the owner, their sessions and the tokens. Migrated by Beamlet itself at boot from the package's priv dir.

Both live under `db/` in the data dir, `agent.db` and `beamlet.db`, with SQLite's `-wal` and `-shm` sidecars beside them. The paths are derived, never configured; adapter options for either repo go under `config :beamlet, <Repo>`. Boot creates each file in WAL mode with a single connection before its pool starts, because a pool opening several connections on a file not yet in WAL mode races to switch it and logs failed connects; `mix ecto.create` would not prevent this, since `storage_up` ignores the adapter's WAL default, so the journal mode is explicit in each repo's `init/2`. The `Ecto.Migrator` child migrates the system database at every boot in every environment, so no consumer runs a migration step and the test suite needs no `ecto.migrate` alias. Since the Migrator reads a missing migrations dir as nothing to run, boot refuses to start without it, naming the path, rather than failing later on a table that was never created. An authorizer on every agent database connection refuses `ATTACH` and `DETACH`, and with them `VACUUM INTO`, which attaches internally, so raw SQL granted to agents stays inside that file. It is exqlite's `authorizer` connect option, set in `Host.Repo.init/2`, which needs exqlite 0.41, so Beamlet declares that floor itself: an older exqlite ignores the option rather than refusing it.

**Beamlet's own tables in the agent database** (2026-09-17, versioned 2026-09-23) are furniture: Beamlet's tables holding the agent's data, marked by the double-underscore names (`__kv` and `__routes`), outside the agent's migration history and inside the unit that wipes and backs up. A second `Ecto.Migrator` over `Host.Repo` lost: `migration_source` is repo config, so the agent's migrations would share it, and Beamlet's history would sit in the agent's database beside theirs. Instead `Beamlet.Tables` is an ordered list of up-only steps, each a list of SQL statements, versioned through `PRAGMA user_version`, the integer SQLite keeps in the file header: the stored version is how many steps have run, and a synchronous child right after `Host.Repo` runs the ones above it in order at boot, so a beamlet skipping several versions runs every step between. A step and its version bump run in one transaction, so a crash halfway leaves the old version and the step reruns; no tracking table, no `IF NOT EXISTS`, and neither Ecto migrator changes. A file above the current version was written by a newer Beamlet, the rollback of an image across a furniture step, and fails the boot with a message naming both versions: up-only steps have nothing to run and no way back, and a beamlet down with a clear error beats one quietly writing to a schema it does not know. Traded away: the free recreation of a table agent code dropped. The promise from 0.1 on: an upgrade never requires a fresh data dir. The system database migrates through Ecto, the furniture through these steps, a change to the code dir or files dir layout ships the move that applies it, and the agent's own tables are never touched. Furniture steps should stay rare; a beamlet that needs them often is a sign the migration story wants revisiting.

### The owner, tokens and principals

Settled 2026-09-14, the two token kinds 2026-09-21, one owner 2026-10-01. The vocabulary first, because the words do the work:

- The **owner** is the person a beamlet belongs to, and its one **user**: a row in the system database (`Beamlet.User`) with an email, a password hash and timestamps. No name and no roles. The email is the sign-in identifier, stored trimmed and lowercased, never verified and never mailed. A check constraint holds the table to one row, so a second user is refused by the database and not only by the code. One owner is what the security model rests on (`context/security.md`): a token that gets past its policy reaches only what the owner already holds, so there are no other users to isolate from it.
- A **token** is the owner's delegation to one client: a random secret shown once at creation and stored as a hash, with a **policy**. The owner holds as many as they have clients, a permissive one and a restricted one used in different places. Delete is delete; nothing references a token row, so there is no revoked state. Two kinds: a `cli` token is named on the command line, never expires and is how the owner's own code connects; an `oauth` token is minted at consent, carries the client id URL as `client`, expires and is refreshed. `Beamlet.Token.label/1`, the name or the client's host, is how either is shown.
- **Authentication** turns the bearer token on a request into its token row. It happens once per request, at the edge, and only Beamlet's own tokens are valid.
- The **principal** is what a request acts as: token id and label, policy name. Built per request from the token, never stored. Every exec, define, commit and route keys on it. The client's name and version are not on it: they are connection metadata, and the token is the provenance. `Beamlet.Principal` is flat, three fields; the encodings below do the nesting.
- **Authorization** is checking what the principal may do, forward looking: the scanner enforcing the policy. **Provenance** is the record a persisted thing keeps of the principal that made it, backward looking. "Identity" is not a term of art here; the principal covers it.
- The **system principal** is what the beamlet acts as on its own behalf: the token `beamlet` with id 0, which the database never issues, under `default`. Named `beamlet` rather than `system` because that is the name already on every commit's committer line, so a reader of `git log` sees one name for the beamlet itself as author and committer; the token name is reserved in the changeset. The boot sweep uses it, so every commit carries trailers and the audit has one shape of commit, and it is the seam a future in-process embedder would hand in. Nothing falls back to it: a `Host.*` function that needs a principal and finds none raises, since the unanticipated case should be loud.
- **A principal is a token acting through a tool; a web identity is the owner on a request; nothing turns one into the other** (2026-09-17). The principal carries a policy because the tools are where code is authored and discovered, and the policy governs exactly those two things; it is ambient in the process only because evaluated code takes no arguments. A served route is neither: its code was scanned when it was defined, under its author's policy, and nothing more is authored when it runs. So a route acts as nobody, the `Host.*` functions that record who acted or filter by policy raise inside one, and a controller action that removes modules or unmounts routes is not a supported case. The signed-in owner is a web identity: the user known to the request, carried on the conn or the socket as Phoenix carries `current_user`, with no token and no policy, since a browser authors no code. If a page ever changes the beamlet, that is the admin UI calling `Beamlet.*` with an explicit record of who acted, not agent code reaching for tool-side verbs.

**Policy attaches to the token.** A policy is a named document (§ 2 Policy says what it contains); Beamlet ships `default`, a token names one and has `default` when it names none. Two policies for one person means two tokens, and the history names the token, so nothing is lost. A request whose token names a policy the config no longer defines fails clearly rather than falling back.

**Identity is per request, with no session binding.** The protocol is heading that way (the 2026-07-28 revision removes sessions) and nothing here needs the alternative: server instructions never depend on the token, so `print_policy` under the request's own token is how a client learns what it may call.

**Management is the shell's.** The public functions of `Beamlet.Owner` and `Beamlet.Tokens` are the product; `Beamlet.CLI` is a thin shell over them. Nothing under `Host.*` reaches the owner or creates, lists or deletes tokens. `Beamlet.Case` creates the owner and one token for every test through the same functions, so every test authenticates the way production does.

The CLI is one function, `Beamlet.CLI.main/1` over argv, printing plain text and returning `:ok` or `:error`, and each environment gets a thin entry that calls it: `mix beamlet` in development, `bin/beamlet` in the release, which has no Mix, so the module is the one implementation. Commands are dotted: `setup`, `tokens`, `tokens.create NAME`, `tokens.update ID`, `tokens.delete ID`, `policies`, `policies.show POLICY` and `reset`. Tokens are addressed by the id `tokens` prints, since an OAuth token has no name; `tokens.update ID` takes a `cli` token only and `tokens.delete ID` either. Delete asks nothing and says what it removed. Each command declares its own switches in the `@commands` table and refuses any other, naming the command's shape, and a declared switch with no value is reported as missing its value (2026-10-01): one strict list for every command let a stray switch pass quietly and reported a missing value as an unknown option. `setup` (2026-10-01) is one command for the first run and every one after: the email, offering the current one, then the password twice, where a blank answer keeps the current password and is refused on the first run, when there is none to keep. The email is checked before any password is asked for, and the run says what changed, or that nothing did. It never asks for the current password: shell access already outranks it, and asking would leave a forgotten password unrecoverable. Piped input answers one line per prompt. Token commands work before `setup`, since tokens hang off nothing. The CLI needs the policies and the system database and nothing an agent reaches: when no beamlet runs in the VM it starts that half of one with `Beamlet.start_link(only: :system)`, runs the command and stops it, so it works beside a beamlet in another VM or with none at all, and a bad policy declaration fails the command with the boot's own error; a beamlet in the same VM is used as it is. `policies` lists the declared names and `policies.show NAME` renders one. `reset` (2026-09-23) is the one command that starts nothing: it deletes the unit agents build, the agent database with its sidecars, the code dir with its history and the files dir, keeps the system database, the operator config file and everything else in the data dir, and says what it removed and that a running beamlet must be restarted. The database goes first, since code without it boots fresh while a database without its code keeps migrations and routes for modules that are gone; a step that fails, a file the CLI cannot remove, stops the reset with the error and a note that running it again finishes the job, since every step skips what is already gone. It detects no running beamlet, in its own VM or another. The CLI is always its own VM, so an in-VM check would never fire in practice; probing the server over distribution would refuse on Fly, where the only shell is on the running machine; and a wipe under a live server does no lasting harm, since the server keeps what it has loaded until it restarts and boots fresh after. `beamlet eval`, a command evaluating code on the running beamlet as the system principal, was dropped: the read it was for, the instructions and descriptions off `Beamlet.MCP.*`, is one line under the release's own `rpc` or `remote` command, or `iex -S mix phx.server` in development, and both a second beamlet booted in the CLI's VM and a distribution link cost more than that.

**Two contexts, structs at the root.** `Beamlet.Owner` owns the user and the sessions, with `Beamlet.User` and `Beamlet.Session` beside it; `Beamlet.Tokens` owns `Beamlet.Token`. Tokens are not a sub-resource of the owner, since with one owner the parent argument would always be the same, so `Tokens` takes conventional arguments of its own: plain `create`, `update`, `delete`, `list` and `find`, beside `authenticate`, `authenticate_refresh` and `rotate`. `Owner` is named for the role rather than pluralised for a table, since there is no collection: `find/0` is the owner, `create/1` the first setup, `update/2` every one after, a new password ending every session in the same transaction, `authenticate/2` the sign-in, and `create_session/0`, `authenticate_session/1` and `delete_session/1` the browser's. The schema keeps the conventional name and the assign stays `current_user`: the owner is a user, the beamlet's only one, and anyone who knows Phoenix reads both at once; `current_owner` lost on reading as though ownership could change hands. The structs stay at the root rather than under a context because `Beamlet.Tokens.Token` stutters. Ecto's own shapes throughout: a failed validation returns the changeset, a miss returns `{:error, :not_found}`. A token name is lowercase letters, digits, underscores and hyphens, at most 64 characters, because it becomes a git author and a trailer value, and unique across the beamlet. The policy default lives on the schema, not the column, so the database records no design decision.

The secret is 32 random bytes as unpadded URL-safe base64, the string a client keeps. Only its SHA-256 is stored, a raw binary under a unique index; a fast hash is right for a secret with that much entropy. `Beamlet.Tokens.authenticate/1` hashes the presented string as it is, with no decoding step, so a malformed value simply matches nothing. The secret rides on a virtual field of the struct that `create` returns and is nil on every token loaded afterwards. Session secrets and OAuth codes are made the same way, and one internal module, `Beamlet.Secret`, generates and hashes all three.

**Tokens are opaque, in one table with a kind** (2026-09-21). A JWT access token needs a signing key that survives restarts and a JOSE dependency, and cannot be revoked before expiry without a denylist, so it needs short lifetimes and therefore stored refresh tokens: the table comes back holding refresh tokens instead of access tokens. What a JWT buys is validation by a process that cannot reach the store, which a single-node beamlet never needs. An opaque secret with its hash in a local SQLite file validates in one indexed read, needs no key, and gives CLI and OAuth tokens one row shape. The `kind` is an `Ecto.Enum` column, `cli` or `oauth`, not a reading of which fields are null, because the kinds differ in several columns already and an implicit rule breaks the day another arrives. A `cli` token has a `name`, required, unique across the beamlet and under the name rule since it lands in a git trailer, and null expiry and refresh fields. An `oauth` token has `client`, the client id URL verbatim, the identity the redirect was verified against, since anyone can host a document that says "ChatGPT"; `expires_at`, `refresh_hash` and `refresh_expires_at` required; no name; and nothing unique on `client`, since a person may authorize the same client twice. Two honest columns beat one overloaded. Refresh rotates in place, new secret and refresh hashes on the same row, so the token id provenance points at survives. The rotation is a compare-and-swap on the old refresh hash, so a refresh secret redeems exactly once even when two requests race; the loser answers as a spent secret. A transaction was the alternative, but under SQLite's deferred mode the loser fails with a lock error rather than a clean answer, and whether it holds at all depends on the database's locking. Two changeset functions, `cli_changeset/2` and `oauth_changeset/2`; the context picks by kind, and the token endpoint refuses to refresh a `cli` token. The principal carries `token_label`, so a trailer reads `Token: laptop (3)` or `Token: claude.ai (7)`.

### Policy

Settled 2026-09-15. Code mode had three mechanisms at three scopes: grants as host-wide config, shape rules per agent, tool access per agent. In Beamlet all of it is one document, and a token names one.

**Policies are guardrails, not containment** (2026-10-01). A policy steers a client: it stops an honest model's accidents and low-effort prompt injection, and the token, not the policy, is the boundary. Agent code runs in the beamlet's own VM, where some ways past a policy cannot be closed without taking the stdlib away, so an escape is closed only when the fix is cheap, steers normal use or completes a rule that already exists. `context/security.md` holds the stance, the classes of escape left open and the rule for deciding.

The vocabulary:

- A **policy** is a named document saying what a token's requests may do on a beamlet. Three parts: tools, rules, grants. One name answers the question.
- **Tools** are which of the beamlet's MCP tools the token may use: `eval`, and `define`, which is two tools in one (2026-09-29). A policy granting `define` lists the `define` and `patch` tools, since both write modules through the same pipeline, the same scanner under the same policy, the same audit and the same compile timeout, and neither restricts anything the other allows; offering them separately was a false choice. Operators do not care, agents see two tool surfaces, and `Beamlet.Policy.tool_list/1` is the expansion.
- **Rules** are the shape rules on submitted code, `allow_defmacro` and `allow_dynamic_dispatch`, strict by default. They are submission rules, not execution rules: they govern what a token may author into the shared pool, never what it may call.
- **Grants** are the name table: a module maps to `:all`, `only` or `except` at function/arity granularity, and absence is denial. The verbs are `allow` and `deny`.
- **`default`** is the policy Beamlet ships: the curated grants, strict rules, both tools. It cannot be declared or changed, every other policy builds on it, and a token has it when it names none.
- The **effective grants** are a policy's grants plus every defined module, granted by existence. The shared pool is the one thing that is not per policy: anything one token is granted reaches the pool through a module it defines, as a macro does under `allow_defmacro`. Accepted once, here, and documented for the operator; not a reason to withhold the lever.
- **Signage** is the teaching copy appended to a refusal, for the few names where "not permitted by your policy" would leave an agent guessing. It is Beamlet-wide, not part of any policy, and a lookup takes the policy so the copy stays true for it.
- The **curation record** is the data behind `default` and the coverage walk that proves every documented platform module has a ruling.

Two kinds of signage earn a place. A **redirect** names the door the agent would not guess: `File` is refused, `Host.File` is where scoped file access lives; likewise `Host.KV` for `Agent` and the ETS family, `Host.Repo` for `Ecto.Repo`, `Host.Router`, `Host.PubSub`, `Host.Migrator`, and the `define` tool for `Code`. A **closure** says a whole family is withheld, so the agent stops walking its siblings; it pays for itself only over a family the model predictably walks, process primitives and the environment (with the reason it may hold credentials, which changes the agent's plan). A policy that grants a signed module never refuses it, so its hint never fires; a redirect whose door the policy withholds is dropped, since a pointer at a closed door is the one hint that misleads. Everything else denied gets the generic copy, and the not-granted record carries the reason.

Retired words: *stance*, *amendment*, *whitelist*, *name policy*, and *code mode* in anything an agent reads, where a refusal says "not permitted by your policy".

**A policy is data, declared in application config, validated and resolved at boot, never stored.** Not a file the library reads, not a module, not a row:

```elixir
config :beamlet,
  policies: [
    explorer: [
      tools: [:eval],                          # replaces the default's list
      rules: [allow_dynamic_dispatch: true],   # merges into the default's rules
      allow: [Task, {File, only: [read: 1]}],  # replaces the module's entry
      deny: [Host.Repo, Host.HTTP]             # removes the entry
    ]
  ]
```

Config is already the one surface, read at runtime, so an embedder writes this in their own config and a release sets it from `runtime.exs` with nothing new to learn. Validation is a function over data: a teaching error names the policy and the key and fails the boot. The alternatives each lost on one point. A DSL file in the data dir is a second declaration surface that evaluates code at boot for what is a document. Rows in the system database suit things the product creates at runtime, and a policy is authored; a dozen entries through CLI flags ends in an import command, at which point the file is the truth and the row a stale copy. A module suits an embedder and is unreachable from a container.

The document, applied as `default`, then `allow`, then `deny`:

- `tools` replaces the default's list when given.
- `rules` merges: a key given overrides, a key absent stays strict, an unknown key fails the boot. New shape rules get a home here without widening the top level.
- `allow` replaces the module's entry wholesale, the default's included, so `allow: [Kernel]` re-enables `apply`, the operator's deliberate call. `only:` and `except:` are relative to the module's full surface.
- `deny` removes the module's entry. It applies after `allow`, so a module in both keys is denied, documented rather than an error; denying a module nothing grants is a no-op.
- Order inside a key does not matter, a module named twice in one key is an error, every module named must be loadable on the beamlet, and every function under `only:` or `except:` must be exported at that arity, as a function or macro, so a typo fails the boot rather than granting nothing.
- Policy names follow the token name rule; `default` is reserved.
- Declare and restart. No reload.

Two keys were considered and left out. `extends` between custom policies: every policy extends `default`, and chains are a speculative need. `allow_app`: which packages exist is a property of the runtime, not of a policy. The default grants the package the beamlet ships for agent code, `jason`, expanded at boot into per-module entries with `@moduledoc false` modules excluded; Req ships too, but agent code reaches it only through `Host.HTTP` (§ HTTP). Jason stays beside Elixir's `JSON` because models reach for it by training, and turning them away teaches nothing. A custom policy speaks only in modules; an embedder granting their own package lists its modules under `allow`, and agent-installed dependencies (§ 4) will decide who grants those. `deny` is per module, so closing HTTP for a policy is `deny: [Host.HTTP]`, and closing a package names its entry points, which is short for any package; a `deny_app` can arrive when a policy needs it. The default also grants every `Host.*` module whole, the framework's web and data rows, and `Macro`'s string helpers (`underscore/1`, `camelize/1`, `to_string/1`); everything that builds or expands code stays denied.

**Enforcement** sits at three edges and one gate:

- **Tools.** The listing is per request: `Beamlet.MCP.Server` overrides `handle_request/2` to filter the `tools/list` reply by the principal's policy, delegating everything else to Anubis. A call is gated in each tool's `execute` through `Beamlet.MCP.Server.authorize/2`, not in the override, because Anubis runs a task-augmented `tools/call` without passing through `handle_request/2`; `execute` is where every path ends. Arguments are validated before `execute`, so an ungranted tool called with bad arguments answers the validation error rather than the unknown tool; the tool names are public, so nothing is revealed. A listed tool is a promise, and a model that never sees `define` never reaches for it. The refusal is the JSON-RPC error Anubis returns for a tool that does not exist, since to that token it does not; an HTTP error on a `tools/call` POST would read as a transport failure to a client. Anubis's own per-component `scopes` reads only its OAuth claims, which Beamlet does not use, so under Beamlet's plug they are always empty. No list-changed notifications: a policy change is a restart.
- **A missing policy.** A token naming a policy the config no longer declares is a 403 from `Beamlet.MCP.Plug` on every request, with a one-line body naming the token and the policy, the shape of the 401 beside it. The token authenticated and the server considers the credential insufficient, which is what 403 means. Failing at `initialize` is what makes it visible to the person connecting the client.
- **The token.** `Beamlet.Token`'s changeset validates the policy name against the declared names (`Beamlet.Policies.names/0`), so the store refuses a token for a policy that does not exist and the CLI's error comes from the changeset. A token whose policy has since left the config is therefore made in tests by writing the row directly, standing in for the restart that removed it.
- **The scanner** is the gate for rules and grants, taking the policy struct. Boot compiles carry no gate, and tightening a policy never evicts a module: adjudication is submission-time only. Struct literals are not checked against the grants (2026-09-30): a struct is a map with a `__struct__` key, which `struct/2`, a map literal or `Map.put` builds under any name, so refusing `%File.Stream{}` stopped nothing, while it refused a schema naming its own inline embed, which does not exist until the schema compiles. `@derive` is refused beside `defprotocol` and `defimpl`: protocols are consolidated at build, so an implementation compiled at runtime is never dispatched to, and the refusal teaches converting the struct to a map instead.

`Host.Code.print_policy/0` renders the calling token's policy, by name: tools, rules in force, the deliberate denials it has not re-granted, partial grants. Its `Tools:` line is the one place that names every tool and marks the ones withheld, `Tools: eval (not granted: define, patch)`, because descriptions and instructions are static per server and cannot know a token's policy: they name tools plainly, and one sentence in the instructions says the policy sets which a token has and points here (2026-09-29, replacing a hedge of "when it is in your tool list" on each mention). The same rendering serves the operator as `beamlet policies.show NAME`.

The shape in code: `Beamlet.Policy` holds the struct (name, tools, rules, grants), `build/2` with the document validation, the grant lookups and `render/1`, its moduledoc the operator's reference including what each relaxed rule reaches; `Beamlet.Policy.Rules`, `Beamlet.Policy.Default` (the curation record, its moduledoc rendered from the data, a golden fixture pinning the composed table) and `Beamlet.Policy.Signage` (`hint/2`, `hint/3` and `denials/1`, with a test proving every signed name is denied under the default) sit beneath it. `Beamlet.Policies` is a `GenServer`, the first child of `Beamlet`, that builds `default` and every declared policy in its init and loads them into an ETS table it owns, so a bad declaration fails the boot, a lookup is one read in the caller with no message to a process, and the policies live exactly as long as the beamlet; `:persistent_term` lost on lifetime, since it outlives the supervisor. `fetch/1` and `names/0` are its whole surface, and `Beamlet.Config.policies/0` reads the declarations. `Beamlet.Scanner` takes the policy struct, `scan_eval/2` and `scan_define/4`, the latter also the module the entry defines, granted to itself; the effective grants' other half, every defined module, is merged into the policy by the caller with `Beamlet.Policy.grant/2`. Policy names are strings everywhere outside config, where keyword keys are atoms; the valid tool names are a list on `Beamlet.Policy`, `tool_list/1` expands a policy's to the tools it lists, and a test checks the server's components match the default's. A test declares the policies its beamlet has with `@tag policies: [...]`, in the shape config takes, which `Beamlet.Case` puts into config before the beamlet starts and removes after; a fixed set in the test config lost on each test saying what it expects.

Deliberately out: exec limits per policy, since they are how much rather than what and stay ordinary config; reload; operator-added signage; a policy built on an empty table rather than on `default`.

### Provenance

One struct, two encodings. A route row stores the principal as JSON in a map column; a commit carries it as git trailers, with the token's label as the author (`laptop <laptop@beamlet>`) and `beamlet` as the committer, so `git log` and `git blame` show which client did it. Both come from the same struct, so they cannot disagree, and both decode back to it:

```
define: Shopping.Item

Token: laptop (3)
Policy: default
```

```json
{"token": {"id": 3, "label": "laptop"}, "policy": "default"}
```

Labels first and ids beside them: the label is what a reader wants, the id is what a program wants after a rename. Time is not in the stamp; git and the row's timestamp already have it. Trailers because git parses them natively, so a future history call filters by token or policy with no code of ours. The route table lives in the agent database, a different file from the tokens, so there is no foreign key to keep and no discrete columns: the set is small enough to load and filter in memory. What carries provenance is every commit the code server makes and every route row. Not KV entries, not files, and there is no eval log. `Beamlet.Principal.to_trailers/1` and `from_trailers/1`, `to_map/1` and `from_map/1` are the encodings, and `Beamlet.Route.principal/1` reads a row's back.

### Eval

Settled 2026-09-16. `Beamlet.Eval` is the runtime behind the `eval` tool: `run(code, principal, opts)` fetches the policy by the principal's name, scans, evaluates and returns the result or the error as text, and `Beamlet.MCP.Eval` maps the tuple to a tool result. Nothing sits between them: the component is the tool. The output contract: what the code printed, then `=> ` and the inspected last expression, with a refused call, an exception, a timeout or a memory kill as error text that keeps the output printed before it. Each run is a fresh evaluation in the beamlet's VM, empty bindings, no prelude.

**Two processes, tied one way.** Anubis runs every request in a task of its own and answers `notifications/cancelled` by terminating that task, so the tool process is Anubis's. The code runs in a child under `Beamlet.TaskSupervisor` so that the timeout and the heap cap can kill it while the tool process survives to report with partial output; the tool process owns the StringIO for the same reason. The child is not linked, since those two kills would take the tool process down, and a monitor alone cannot tell the child its caller was cancelled, which would leave the code running to its own timeout after a cancel. Erlang has no one-way link, so a watcher provides it: a third process monitors the tool process and kills the child when it goes. Trapping exits in the tool process lost, since it sets a flag on a process Anubis owns and makes the runner answer the supervisor's shutdown itself. Closing the HTTP stream cancels nothing in Anubis 2.0; the notification is the only cancel signal.

**Three limits**, `config :beamlet, eval: [...]`, each named for what it protects: `timeout` (30 seconds) the session, since a session runs one request at a time; `max_heap_bytes` (256MB) the beamlet; `max_output` (16KB) the model's context. The MCP request timeout must be longer (§ MCP): it is a call timeout that answers "Server unavailable" and leaves the request running, so it must never fire first. 16KB because inspected Elixir runs three to four bytes a token, which puts a full result at four to five thousand tokens, under Claude Code's 10,000-token warning (its default cap is 25,000, past which it writes the result to a file and hands the model the path), and because the inline tail teaches where a client's file fallback does not. The inspect limits are constants; nobody tunes how one value renders per beamlet. Agents get no per-call limits; `opts` on `run/3` are for tests.

**The ambient principal.** Evaluated code takes no arguments, so the runner puts the principal in the child's process dictionary before the code runs (`Beamlet.Principal.put_current/1`) and the stdlib functions that must record who acted read it back (`current/0`); outside evaluated code it is nil. The value is the principal alone, and the policy is fetched by name. A tool that holds the principal passes it explicitly.

### Define

Settled 2026-09-16, the module as the unit 2026-09-28. `Beamlet.Define` is the runtime behind the `define` tool, the shape eval set: `run(entries, principal, opts)` fetches the policy, and for each entry parses and formats it, scans (`Beamlet.Scanner.scan_define/4`), runs the docs gate (`Beamlet.Code.Docs`) and hands the modules to the code server; `Beamlet.MCP.Define` maps the tuple to a tool result. The define semantics came over from code mode whole: modules not files, one canonical file per module under `code/lib`, docs enforced because they are the discovery surface, the two collision tiers with `replace: true` as permission rather than assertion, dependents recompiled on a replace and provable breakage refused with nothing changed. The reserved prefixes are `Beamlet.*` and `Host.*`. A module's file is named for its underscored name, which folds case, so `HTTPClient` and `HttpClient` share one; a define placing a module at a path another defined or quarantined module holds, or two entries of one call at one path, is refused naming both (2026-09-30), since otherwise the second define renames its file over the first's source and the first vanishes at the next boot.

**Generated modules** (2026-09-30). The defined set is what the files declare with top-level `defmodule`, at define and at boot alike. A macro can create more modules as a file compiles, an inline `embeds_one` or `embeds_many` schema, or the `Inspect` implementation Ecto derives for redacted fields; those are generated, each owned by a module its file declares. They load and keep their beams, but are not defined: not listed, not granted as call targets, and refused by name to define and to remove, the refusal naming the owner. They go with the owner: removing it unloads them and deletes their beams, a replace unloads the ones it no longer produces, a failed define unloads any it newly loaded and restores the previous ones, and their edges and calls count as the owner's. Before, boot admitted every compiled module to the defined set, so a generated module became removable after a restart, and removing it deleted its owner's source file.

**The code server is `Beamlet.Code`**, a GenServer child of `Beamlet` owning `<data_dir>/code` (`lib/`, `ebin/`, `.staging/`, `.git`), with `Beamlet.Code.Tracer`, `Beamlet.Code.Docs` and `Beamlet.Code.Audit` beneath it as internals. `compile_artifact/2` is the derived compile the route generator uses, of quoted form rather than source: it runs in the server's lane because the compiler options and tracers it swaps are VM-global, and writes nothing. It takes a function returning the quoted form, run inside the lane too, so the router is built from the table as it stands when the compile runs; built in the caller, two regenerations racing could land an older table over a newer one and drop a fresh route (2026-09-30). It keeps the last good binaries per file, because a module body that raises partway through a compile unloads the previous version; on a failure it loads them back, so the previous router really does keep serving. Remove is the server's second operation and the audit's second commit kind; its mounted-route check sits beside the dependents check so it is atomic with the removal.

**One table.** The server records everything it collects in a named public ETS table it owns: the compile context the tracer reads, the compiled beams, the edges and call records of the compile in flight, the defined set with its paths, and the quarantine, so `manifest/0`, `quarantined/0` and `defined/0` are table reads. The defined set is the effective grants' other half: an eval's scan never queues behind a thirty-second compile, and both runtimes merge it into the policy with `Beamlet.Policy.grant/2` before scanning. Define and patch use the same function to grant a call's own modules to each other, so two quarantined modules that call each other can be repaired in one patch. Rows are added before stale ones go, so a scan in flight never sees a defined module missing.

**Cancel is an abort.** The tool process is Anubis's and a client cancel kills it, so the server monitors the caller for the life of the define: a define still queued behind another never starts, a compiling one is stopped and rolled back to the previous beams, and one past the commit point completes. A remove gets the same queued check (2026-09-30), since `Host.Code.remove` runs in an eval that a cancel or the eval timeout kills, and without it a remove queued behind a compile would go ahead after its caller had been told it failed. The check is `Process.alive?/1` after the monitor, not a `receive` with `after 0`: the DOWN for a process already dead arrives as a signal the receive can run ahead of. Eval needed a watcher process because its caller must survive the kill of its child; here the server is long-lived and holds the monitor itself. The parallel compiler monitors its workers rather than linking them, so stopping the compile kills the task and the workers it is watching, on cancel and on timeout alike.

**Git is a requirement, not a mode.** The history is the provenance record, and a flag to skip git is a mode where defines leave no trace. A beamlet whose PATH has no git fails to boot with a teaching error, the repo is initialised at boot with the initial snapshot and hand edits swept into a commit of their own, and the image installs git. The repo carries no configuration: every commit names the token as author (`laptop <laptop@beamlet>`) and `beamlet` as committer through environment variables on the command, which also keep git's automatic maintenance in the foreground (2026-09-23), since git 2.47 detaches it and it would go on touching `.git` after a commit returns, racing a reset or a test's wipe, with the principal as trailers in the body, and the sweep commits are authored by `beamlet`. The sweep says what it found: one warning listing git's status lines before the "manual changes" commit, since a hand edit to the code dir is unusual enough to surface to the operator, who reads the VM log and nothing the agent sees, and the commit it names is the point to roll back to. Empty commits are allowed so a replace with the same source is still on the record. A test suite boots a beamlet ninety-odd times and each boot pays git's forty milliseconds; a couple of seconds is not a reason to shape the design.

One limit, `config :beamlet, define: [timeout: 30_000]`, the time one compile may take, for define and patch alike; the MCP request timeout must be longer (§ MCP). The principal is required on `define` and `remove`. `Beamlet.Case` wipes the code dir before each beamlet starts, so every test boots with no defined modules and a fresh history.

**The module is the unit** (2026-09-28). `define` takes a list of entries, one top-level `defmodule` each with its own `replace` permission, and the code server takes modules with their sources, paths and kinds. A module's path follows from its name, `lib/shopping/list.ex`, a migration's from its `use Ecto.Migration` line, decided before the compile. The entries land together or not at all; a model wanting per-module outcomes makes one call per module. Lost: a single buffer split internally, since models write one file per tool use and the split was the one step that made line numbers mean something the model never wrote; a per-call `replace` flag, over-broad in the mixed case; and partial success, since whether a replaced module can land when its caller in the same call failed depends on the caller's old version, a rule hard to state. `Beamlet.Code.Entry` holds the per-module steps define and patch share: the parse, the one `defmodule`, the kind, the path and the rule naming it, the scan and the docs gate, which takes the module and body the parse found rather than parsing again; and the AST helpers the other readers of module source share (2026-10-01). `Entry` finds the one `defmodule` and the scanner refuses anything beside it, an expression or a protocol, since the scanner reads the formatted text every locator indexes (2026-10-01).

**Source is stored formatted, and formatting comes first.** Each module is parsed and formatted before the scanner, the docs gate or the compiler sees it, so there is one text per module from the first error to the stored file and every line number in the pipeline indexes it; the formatter is pure and cannot fail after a successful parse. Its rules are Elixir's defaults plus the no-parens locals read at compile time from the `.formatter.exs` exports of phoenix, ecto, ecto_sql and plug, so `plug :auth`, `attr` and `slot` stay bare; the HEEx plugin stays out, so `~H` content is verbatim; nothing is configurable. The costs: the code dir no longer reads byte-for-byte as authored, and a same-session patch quoting the agent's own unformatted text may miss, which the no-match error explains. Normalising order was rejected: guards and macros must precede their uses, `attr` sits directly above its component and `plug` calls are an ordered pipeline, so a reorder silently rewrites what the agent meant, where `select` with `before` and `after` buys placement without rewriting.

**One locator form: `lib/shopping/list.ex:42`.** Every location an agent reads, from the scanner to a compile error to a runtime stack trace to `print_source`, is the module's path relative to the code dir and a line of its stored source. The staging path never reaches an agent: compile diagnostics attribute by file and render through this form, an exception raised while a module body runs, which the compiler reports at line 0 with its trace, takes its line from the trace's frame in the failing file and has the trace formatted again with every file under the code dir or the staging dir as its locator (2026-09-30), and eval maps the frames of defined modules through the manifest before formatting a trace, so a module reads the same before and after a restart. Every error quotes the offending line, so on a failed define, where nothing is stored, the number is a hint and the text the locator that always works. The exceptions come before a module exists: a syntax error names the entry by its `defmodule` line or its position in the list, and an eval's scan errors keep `line 3:`, since an eval buffer is not a file. Nothing about line numbers is taught in the descriptions.

**Scattered clauses are refused** (2026-09-27), at define, patch and boot. Elixir only warns when clauses of one function are separated by other definitions, so a `select` could otherwise meet a non-contiguous block. The code server filters `compile_warnings` for the arity variant of the warning and refuses as a compile failure, one line per function in the locator form; a hand-edited scattered file is quarantined at boot, since hand edits follow the same rules as the tools. `a/1`, then `b/0`, then `a/2` stays legal, since different arities are different selections. A test pins the compiler's wording across the CI matrix.

**A replace says what it changed.** Under `Defined X (replaced)` and `Patched X`, one bullet per kind names the functions removed, changed and new in source order, with the clause count when it changed, since an accidental second clause is what Elixir accepts with at most a warning while the old clause keeps matching; a function is changed when its block's text differs, docs included, so a tidied docstring shows. The empty cases have a bullet each, `unchanged`, `no function changes`, and `previous source did not parse, so nothing to compare`, so the model knows the comparison ran. `Beamlet.Code.Source.diff/2` reads the old file at the top of the commit, the last moment it exists. The same bullets are the commit's body (2026-09-29), under each replaced module's bare name between the subject and the trailers, so `git log` says what a change did without `-p`; a new module has nothing to compare and is left out, and a commit with no replaced module has no body.

### Patch

Settled 2026-09-26, landed 2026-09-27 to 2026-09-29. Before it an agent changed a module by printing its source and defining it whole again with `replace: true`: a one-function change to a 200-line module cost a 200-line print and a 200-line re-emission, re-emission is where a model tidies a docstring or drops a clause, two writers to one module lost the first update silently, and a module past about 450 lines could not be printed under eval's output cap and so could not be replaced safely at all. Every coding agent moved from whole-file writes to anchored edits for these reasons; the 0.1 walkthroughs are where to measure it here, since `git log -p` in the code dir shows every hunk the transcript did not ask for.

**The `patch` tool** takes a list of patches, each a module, exactly one anchor and exactly one operation, applied in order to in-memory copies of the sources and then run as one transaction through the define pipeline: format, scan under the patching principal's policy, docs gate, compile with dependents, broken-caller check, one `patch:` commit; on any error nothing changes. `find` anchors text occurring exactly once in the module's current source, a string operation with no separator logic. `select` anchors a function as `name/arity`, any visibility, macros, guards and delegates included: a block operation over whole lines covering all its clauses and the function-level forms directly above the first. `replace` swaps the anchor, empty removes it; `before` and `after` insert around it, a `select` insertion trimmed of blank lines and separated by one. There are no anchorless patches: appending is `select` on the last function with `after`, which sends the agent through the outline where a duplicate name would show, and a blind append is the one path to a duplicate clause that never runs. A quarantined module is patchable by `find`, since a one-line fix is the natural recovery, and may take several patches to parse again; `select` needs a source that parses. A pending migration is patchable and an applied one refuses, as for replace; renaming the `defmodule` line is refused, since the pipeline would file a new module and leave the old. A no-op patch is a summary and an empty commit. The keys present are the type: the flat schema of six optional strings says less than the truth, the rule is carried by the field and tool descriptions and enforced in the runtime, and whether a precise `oneOf` schema would guide models better waits on sessions to watch (§ 3). The patcher's policy governs the whole resulting module, so a one-line patch can be refused on a line the patcher never wrote, as a replace already is; code ownership is deferred (§ 4).

**Why a tool and not a form in define.** A `defpatch Mod, drop: [...] do ... end` form inside the define buffer was designed first and set aside: a form that exists nowhere in Elixir must be learned from the description, every open question in its design was about its mini-language, its function-level floor fails on exactly the headline case, a `render/1` too long to print whole, and find-and-replace is the most practised tool shape these models have. The third tool costs a description in every session, a listing row and a policy surface, all bounded. Also lost: a single-edit tool, since every write compiles and a change to a function and its callers has no compile-valid intermediate state, so the list is what makes the tool a transaction; `merge: true` on define beside `replace: true`; implicit upsert, where a reader of the buffer cannot tell a whole module from a partial one; clause-level selection by ordinal, a line number in disguise, since a clause's only stable identity is its head text, which is a `find` anchor; and `Host.Code.edit/3` from eval, two strings inside Elixir inside JSON where a module's own `"""` docs terminate the heredoc.

**Selections are what the parser sees**, `Code.string_to_quoted/2` with token metadata and no text heuristics. A block ends at the last line of its last clause, a one-liner's from `end_of_expression`, and starts by walking upward over the forms that belong to a function: `@doc`, `@spec`, `@impl`, `@deprecated`, and Phoenix's `attr` and `slot`, named as a curation record beside the framework module list, since the general rule, any adjacent bare call attaches, would swallow a `plug :auth` above an action. Anything else stops the walk, so a `@default_limit 10` directly above stays where it is. Comments never attach: they are not forms, and the docs gate steers agent code to `@doc`. A function with default arguments is listed by its head's arity. A hand-edited scattered file in quarantine is the one place `select` meets a non-contiguous block, and it refuses with a pointer at `find`.

**The stale-read guard.** The runtime reads outside the code server's lane, and the window to the write includes the scan, the docs gate and the queue behind a compile of up to thirty seconds; a write inside it would be overwritten from the patch's copy. So the runtime hashes the source it read, per touched module, and the server hashes the file inside its lane and compares: different refuses with "changed while you were patching it, read it again", a removed module with its own wording, and nothing changes; the retry is a fresh read and the same patches. Compare-and-swap per module, one hash each. A lock lost, since it would hold every other agent for the scan-and-queue duration and need releasing on cancel and crash for a conflict that is rare; moving the read into the lane lost, since the scanner and docs gate need the patched text and would move in with it. Define with `replace` has the same problem with no read to guard and stays last-writer-wins.

**Every error is teaching and nothing changes.** No match names the module and the first line of `find`, says when the text matches once with leading whitespace ignored, and says that source is stored formatted, so text quoted from a define in the same session may differ from what `print_source` prints. Several matches gives the count. An unknown function under `select` lists the module's functions. A pipeline error names the patch that produced the module, `patch 2 (Shopping.Cart, select total/1): ...`, or all of them when several touched it, and quotes the failing line with two lines either side, since the patched text exists nowhere readable.

The shape in code: `Beamlet.Code.Source`, `@moduledoc false`, pure over text and never compiling, holds `outline/1`, `select/3`, `lines/2`, the splices, and `diff/2` with `render_diff/1`. `Beamlet.Patch` is the runtime in `Beamlet.Define`'s shape and hands the code server define's entries plus a hash and a label; `Beamlet.Code.define/3` takes `verb: :patch` for the compare, the `Patched` summary and the `patch:` commit. `Beamlet.MCP.Patch` is as thin as define's component.

### Discovery

Settled 2026-09-16, reading in pieces 2026-09-28. `Host.Code` is the agent's discovery entry point and the module teardown verb: `print_modules`, `print_docs` at three arities, `print_outline`, `print_source` at three arities, `print_policy` and `remove`. The print contract: a `print_*` function prints and returns `:ok`, `remove` acts silently and returns `:ok`, and a failure raises with a teaching message, so it is unmistakable and eval keeps everything printed before it. The rendering is `Beamlet.Code.Discovery`, `@moduledoc false`, returning `{:ok, text}` or `{:error, text}`, since the print contract is not something a test can assert on as text.

**Every function requires the ambient principal** and raises a teaching error without one ("works from eval, where your code acts as you"). The listing and the docs are filtered by a policy only the principal names, and a removal is recorded against one; a call from a web request or a process of the agent's own has neither, and no policy is an honest fallback, since a custom policy may be wider or narrower than `default`. Discovery takes the **effective policy**, the principal's with the defined modules merged in, exactly as the runtimes build it before a scan, so a defined module is granted like any other.

**The listing is `code/lib`.** Four sections, in order: the modules defined with `define`, each with its moduledoc's summary (the first paragraph on one line, ExDoc's rule, which the define "already exists" error quotes too), followed by any quarantined module with its error and the way out (patch it, define it again with `replace: true`, or remove it), since the listing is the one place an agent learns why a module vanished; the `Host.*` modules; the framework modules, the curated web and data authoring surface (`Beamlet.Policy.Default.framework_modules/0`); and the libraries, one line per package the beamlet ships, led by its primary module, with any module granted from another package on a line of its own. A package's line carries a curated description where its own says nothing, else the `.app` description. The platform is never listed, nor are exception structs. Docs are served from compiled artifacts: a defined module by its beam path, everything else by name, so a granted package is self-documenting. `Host.Repo` joins `Ecto.Repo`'s callback docs onto its generated functions, the one special case. A refused module or function gets the scanner's own copy, so a refused `print_docs` carries the same signage hint a refused call does. `print_source` serves defined and quarantined modules and nothing else. Migrations are not listed: `Host.Migrator.print_migrations/0` is their home and speaks in version numbers, and a web module carries no route suffix, since the URL surface is `Host.Router.print_routes/0`'s. A one-line footer after the libraries points at `print_docs`, `print_routes` and `print_migrations`, so the one print an agent is steered to names the other three.

**Reading in pieces.** `print_outline/1` prints a module's structure with line ranges; `print_source/2` prints one function at every arity or a `Range` of lines, and `print_source/3` one arity, all rendered through `Beamlet.Code.Discovery` over `Beamlet.Code.Source`; no string form, since one way is the house rule. A function or range print is the stored text verbatim with no line-number gutter, so what an agent copies is what a patch's `find` will match, and the numbers live in the outline. The outline shows what a module is made of and hides how it works: functions with their selection ranges and clause counts, types and callbacks with their docs rolled in, `@behaviour`, and every other top-level form by its first line cut at sixty characters, so `use`, `schema` and `plug` appear with no list to curate; hidden are the moduledoc, attributes holding values and an orphaned `@doc` or `@spec`. A denylist rather than an allowlist because the safe error is a superfluous row, and the header carries the line count so every gap is visible and readable by range. A module that does not parse has no outline: the error points at `print_source` with a range and at `find`, and boot reads a torn file's module names from its `defmodule` lines so it is listed as quarantined rather than vanishing.

**Tools and grants are independent.** The default grants `Host.Code` whole, so a policy with `tools: [:eval]` cannot define or patch modules but can remove them. Kept, because coupling them would be the first place a tool implied a grant; a token that should not tear modules down gets `allow: [{Host.Code, except: [remove: 1]}]`, documented on `Beamlet.Policy`.

### PubSub

Settled 2026-09-16. `Beamlet.PubSub` is the beamlet's message bus: one `Phoenix.PubSub` registered under that name as a child of `Beamlet`, and the name is the whole thing; a module for it was written and dropped, since nothing called it. The one line an embedder needs, `pubsub_server: Beamlet.PubSub` on their endpoint, is in the `Beamlet` moduledoc beside the child list. `Host.PubSub` is `subscribe`, `unsubscribe` and `broadcast` over it, with topics one shared namespace the moduledoc tells agents to prefix. `broadcast_from` waits for something to ask.

### Files

Settled 2026-09-16. `Host.File` is `File`, scoped to `<data_dir>/files`, the root `Beamlet.Config.files_dir/0` names and the boot creates. The name follows `Host.Repo` for `Ecto.Repo` and `Host.PubSub` for `Phoenix.PubSub`: the leaf name of the module it stands in for, so an agent's `File` priors are right rather than corrected by an index. The functions are `read`, `write` with modes, `ls`, `mkdir`, `mkdir_p`, `rm`, `rmdir`, `cp`, `cp_r`, `rename`, `exists?`, `dir?` and `regular?`, each returning what `File`'s does, `{:error, posix}` included, with a bang variant raising what `File`'s raises, `File.Error`, `File.CopyError` or `File.RenameError`, naming the path as the agent wrote it. All three are in the granted exception family, so a `rescue File.Error` written from priors works. `ls_r` is the one function `File` lacks: a recursive listing as sorted root-relative paths, the thing agents most often want. Two deviations from `File`, each documented once: writing, copying and renaming create the parent directories they need, saving an eval round trip, and `rm` answers `:eisdir` for a directory where `File.rm` says `:eperm`. Left out: `stat`, since `File.Stat` is denied and nothing asks for size or mtime yet; `rm_rf`, since on a shared root file-only removal bounds cross-user accidents; `cp`'s options, whose `on_conflict` callback would see host paths; `wildcard`.

Tuples and bangs both, not raise-only: the same module runs in controllers and LiveViews, where a missing file is a 404 to handle, not a 500. One shared root, stateless resolution that needs no principal and so works the same from an eval, a web request or a LiveView, a leading `/` meaning the root, every path containment-checked, error copy that never shows a host path, no git audit and no size caps. An escape or a non-string path raises `ArgumentError` from tuple and bang alike: misuse of the API, not a condition to handle. Containment is lexical through `Path.expand`; only an operator can plant a symlink under `files/`, and that is accepted rather than resolved on every call. One module, tested directly under `Beamlet.Case`, which wipes `files/` per test. The scanner expands aliases before its check, so `alias Host.File` lets agent code read exactly as `File` code: allowed and not advertised, since the visible `Host.` prefix is what tells a reader of `print_source` that the scoped door is in use.

### Key/value

Settled 2026-09-17, values 2026-09-29. `Host.KV` is durable storage for small state under string keys: `fetch/1`, `get/2` with a default, `put/2`, `delete/1`, `all/1` and `keys/1` under a prefix with an empty prefix meaning everything, and `delete_all/1` under a prefix with no default so wiping everything is written deliberately. Values live in the `__kv` table of the agent database, so a put inside a `Host.Repo.transaction` lands with the agent's own rows. Keys are one shared namespace the moduledoc tells agents to prefix, as with PubSub topics. `fetch/1` exists because a stored `nil` and a missing key are different answers and `get/2` cannot give both; `fetch!/1` does not, having no scenario.

**Values are strict JSON** (2026-09-29): `nil`, booleans, numbers, UTF-8 strings, lists, and maps with string keys, stored as JSON text through Elixir's built-in `JSON`, and what goes in is what comes out. Raw SQL on `Host.Repo` writes `__kv` as freely as the agent's own tables, so what Beamlet reads back from it is untrusted input, and the format must be unable to express anything but data. External term format could express a fun: hand-built bytes naming any loaded function decoded into a value that `f.()` calls, past the scanner. Lost: external term format with a walk refusing funs, pids, ports and refs after decode, which fails open to whatever the walk forgets; CBOR under a private codec for atoms, which keeps atom keys and values at the cost of an encoder to own and atom decoding to police; and stringifying atom keys, which breaks the round trip where `get(k)[:count]` quietly returns `nil`. `put/2` checks the value before encoding, failing closed, since `JSON.encode!` would write an atom as a string and a struct as its encoder chooses; a refusal is an `ArgumentError` naming what was found, where in the value it sits (a path of map keys and list indexes) and what to store instead, and nothing is written. Anything `JSON.decode` returns is plain data, so a read needs no check; a row that is not JSON text, which only raw SQL can write, raises naming the key and `delete/1`, which never decodes. `nil` is the text `null`, so the column is `TEXT NOT NULL` and a stored `nil` stays distinct from a missing row. `Host.KV` encodes and decodes, and `Beamlet.KV.Entry` beneath it maps the table with a plain string field. A granted schema for agents to query the table through `Host.Repo` was declined: the only key-shaped operations it would open are the ones the module already has, at the cost of pinning the table name and the encoding as public API. Agent SQL can read values with `json_extract`; that is accepted, not advertised.

### HTTP

Settled 2026-09-29, slimmed 2026-10-01. `Host.HTTP` is agent code's HTTP client: `get`, `post`, `put`, `patch`, `delete`, `head` and `request`, each with a bang variant, taking the same arguments as its namesake in `Req` and answering with a `Req.Response`, so Req's documentation and the models' Req priors both apply. Req itself is not granted, only `Req.Response`, Req's exception structs and `Host.HTTP.BlockedError`.

**Why the door exists** (2026-10-01): it is the one place an outbound guard can live. Since policies are guardrails, not containment (`context/security.md`), the door no longer tries to close every way agent code could make Req's code act for it. It was first built to, with a fail-closed allowlist of options, value-shape checks on every option that takes code (`{mod, fun, args}` for `base_url`, `auth` and `aws_sigv4`, module decoders), refusals of `File.Stream` bodies, and wrappers stripping Req's step functions from the request handed to `into` and `retry` functions. All of that stopped only a deliberate escaper, who keeps easier routes, such as module names in data position, and it is gone.

**The outbound guard.** A request step appended after Req's own, so it sees the final URL and Req runs it again on every redirect hop, calls `ReqSSRF.check/2` (http and https, public IP literals accepted) and halts a refused request with `Host.HTTP.BlockedError`, which skips the error steps so it is never retried. Requests to loopback, private networks, link-local and cloud metadata addresses, and names resolving to them, are refused by default; injected text saying "fetch this URL" is the low-effort attack the guard is for. This reverses the earlier deferred note that a household beamlet could not default to blocking the LAN: the operator opens what it needs with `config :beamlet, http: [allow: [...]]`. A name entry matches a URL's host exactly, ignoring case, and skips the check; an IP address or CIDR block matches a host written as an address. A name that resolves into an allowed block is still refused, so the rule needs no resolution of its own. The guard is per beamlet, not per policy: which networks matter is a property of where the beamlet runs, not of which client is calling. Not `ReqSSRF.attach/2`, whose per-request `ssrf_check: false` would have skipped redirect hops too for an allowed host; registering no option also leaves the agent no switch to turn the guard off. The error is a tuple from the plain function and a raise from the bang, like a transport error, since a redirect can be refused mid-request. Its message is Beamlet's for `:reserved_address`, the reason that is Beamlet's rule, and ReqSSRF's for every other reason, so a reason ReqSSRF adds or renames degrades to its wording rather than breaking; the URL is stored without userinfo. Accepted, from ReqSSRF's own limits: DNS rebinding, since the name is resolved again when the connection is made, and a name whose AAAA record is reserved being refused though Req connects over IPv4. To call its own routes an agent uses `Host.Router.call/4`, which the moduledoc points at.

**What is still refused**, as an `ArgumentError` from tuple and bang alike naming the option and what to do instead: what sends a request somewhere the guard never checked or keeps it on disk. The adapter must be `Req.Finch`, and `plug`, `unix_socket`, `connect_options` (a `proxy` connects to a host the guard never saw), `finch`, `finch_request`, `cache`, `cache_dir` and `auth: :netrc | {:netrc, _}` are refused. `into: :self` is refused as steering, since `Req.parse_message/2` is not granted. It is a denylist: every other option is Req's to validate, and Req refuses one it does not know ("unknown option :bas_url. Did you mean :base_url?"), which was all the allowlist's typo-teaching did. Lost: an option a later Req adds that bypasses the network passes until someone reads the Req bump. The check is on the built struct, `Req.new() |> Req.merge(opts)`, so options arrive as Req will act on them (`plug:` has become the adapter) and `plugins:` is refused by `merge` before any plugin runs. The test seams are `config :beamlet, Host.HTTP, req_options: [...]`, merged after the check, and `resolver:`, handed to the guard, as with `Beamlet.OAuth.Clients`.

Deferred: builders for requests built as data (`Host.HTTP.new` and `merge`); `into: :self` with `Req.parse_message/2` and `Req.cancel_async_response/1`.

### Migrations

Settled 2026-09-17. A migration is a plain `use Ecto.Migration` module through the define tool, recognised by its `use Ecto.Migration` line before the compile, with a module that comes to export `__migration__/0` another way refused after it, and filed under `code/migrations/NNNN_name.ex` with a version the beamlet assigns: one past both the files on disk and the versions the agent database records as applied, in call order, so a git rewind that removes an applied migration's file cannot see its number reused and the migration silently skipped. A replaced migration keeps its version and file; a replace that changes a module's kind moves its file between the roots. Define never applies: the summary line carries the pending cue. The pending rule: a migration is editable until it has run, and an applied one refuses replace and remove until rolled back, so the applied stack and the files never disagree. Boot compiles both roots in one batch and the audit commits both.

`Host.Migrator` holds the verbs, `migrate/0`, `rollback/0` and `print_migrations/0`, printing as they go and returning `:ok`, with `Ecto.Migrator.up/4` and `down/4` against `Host.Repo` one migration at a time so a mid-batch failure leaves the earlier ones applied and names the one that failed. `Beamlet.Migrations` is the history they and the code server share: the applied versions and the join of the manifest with Ecto's own `schema_migrations` table. An applied version whose module is gone is an orphan, which only an operator can make since the pending rule stops an agent: the version floor counts it, the listing marks it as applied with its source missing, and rollback refuses past it with a teaching error, because Ecto would otherwise undo the migration beneath. The sweep log surfaces the hand edit that caused it.

### Config

One surface: `:beamlet` application config, read at runtime through `Beamlet.Config` accessors, so a release or container sets it from the environment in `runtime.exs`. No start options carry configuration, nothing is read at compile time, nothing is stashed. Checked once, read plainly after: `Beamlet.Config.validate!/0` checks every key first thing in `Beamlet.init/1`, on both boot paths, and fails the boot naming the key at fault; the accessors then return what was checked with defaults merged and never raise. Validating in each accessor lost: it spread the boot's job across every caller and made runtime paths look fallible when a change is a restart. `data_dir` is the root everything a beamlet persists lives under; starting checks the dir exists and fails the boot otherwise, and the modules owning paths beneath it add their accessors as they arrive: `db/`, `code/` and `files/`. The `http` group holds the hosts agent HTTP may reach on private networks (§ HTTP). The web surface is the `web` group, `endpoint` and `prefix`: the full boot fails without an endpoint, since the routes are served through it, and the system half needs none. A prefix under `/beamlet` is refused, since the beamlet's catch-all there would answer every agent route with a 404. Tests use one data dir per run, `tmp/test_data` in the repo, wiped at the start of each run; a test that needs its own directory gives it to the component directly rather than through config. The one surface has a second source in a container: a release merges an optional operator config file, `<data_dir>/config.exs`, into it through `Beamlet.Config.Provider` (§ Deployment). Mix runs no config providers, so in development each project's `dev.exs` imports the same file from the shared dev data dir when it exists, and a dev policy is declared once rather than in both projects.

### MCP

`Beamlet.MCP.Server` (Anubis, Streamable HTTP) runs as a child of `Beamlet` and serves three tools, `define`, `eval` and `patch`. Unprefixed: the protocol makes names unique per server and clients namespace across servers themselves (Claude Code shows `mcp__beamlet__eval`), so a `code_` prefix would only repeat the server name. `eval` rather than `exec` because the tool evaluates an expression and returns its result, which is what Elixir calls it. Schemas carry only what the tool needs; there is no per-call description field, since the client owns its UI and already shows the arguments. A host serves the tools by forwarding to `Beamlet.Router`, which mounts `Beamlet.MCP.Plug` at `/beamlet/mcp`, under the beamlet's reserved segment.

**The request timeout** (2026-09-30) is a setting of its own, `config :beamlet, mcp: [request_timeout: 65_000]`: how long the transport waits for any request before answering "Server unavailable" while the request runs on. It must outlast the tools' own timeouts, whose errors say what happened, so `Beamlet.Config.validate!/0` refuses one not greater than the larger of the eval and define timeouts. Deriving it from them lost: a define may wait behind any number of others, so no formula over the two limits bounds a request, and a derived number only looked like one. Anubis's HTTP plug takes the timeout in `init/1`, which runs when `Beamlet.Router` compiles, so `Beamlet.MCP.Plug.call/2` sets it in the transport opts per request from config; the server-level `request_timeout` reaches only the stdio transport and is not passed.

Server instructions and each tool description are held under 2,048 bytes by tests: Claude Code truncates both at 2KB, and bytes are the conservative measure against a client counting characters. The instructions are a pointer block, what matters most first and the stdlib for the rest.

**Where context lives** (2026-09-18). Instructions and descriptions land in every session of every client that has the server configured, including sessions that never touch the beamlet, so the static footprint is kept well under the cap rather than at it: the instructions around 1.7KB, `define` around 1.6KB, `eval` around 1.4KB, `patch` around 0.9KB, editorial targets the tests do not pin. The spike licensed that: clients cut at 2KB did the work as well as one that delivered the whole 15KB block, so the descriptions and the teaching errors carry what matters at call time and the instructions mostly buy polish. Context sits on a ladder, and a piece goes on the lowest rung that still reaches the model in time. The **instructions** carry what a model needs before its first tool use: what a beamlet is, the tools in a sentence each, the first calls to make, and the five slips the spike saw models make (fresh bindings per eval, `print_*` prints and returns `:ok` and several fit in one eval, `import Ecto.Query`, other agents and earlier sessions have built there so read first, verify with `Host.Router.call` before reporting done). They are static per server and cannot know a token's policy, so one sentence says the policy sets which of the three tools a token has and points at `print_policy`, whose `Tools:` line names every tool and marks the withheld ones (§ 2 Policy); every other mention names tools plainly. A **description** is that tool's call-time contract, with the configured limits interpolated: for `eval` the empty bindings, the output shape and cap, "end with `:ok`", the timeout; for `define` the entry rules, reserved names, the docs gate with its framework exemption, what `replace` does to dependents and mounted routes, migrations filed pending; for `patch` the anchors and operations, the transaction, read before you patch, and define's rules holding for the result. A **moduledoc** carries the conventions of one module, served by `print_docs`: `~H` templates, `~p` inside them, `<.link navigate>` against a plain anchor, the layout and Tailwind, and live updates through PubSub on `Host.Web`; the query import, `:map` keys as strings and one statement per `query!` on `Host.Repo`; the rollback-replace-migrate loop and SQLite's column-change recipe on `Host.Migrator`; replace-not-remount on `Host.Router`. A **teaching error** carries the correction at the moment of the slip, and a **print** carries state, never conventions. Neither `print_environment` nor a page-per-topic wiki earned a place: the listing's footer names the other prints, and every convention had a module to own it (§ 4, virtual paths).

**The `eval` description is the floor** (2026-09-20). The claude.ai app drops server instructions entirely (anthropics/claude-ai-mcp#93), and in a tool-rich session shows about eighty characters of each description until the model loads the tool; the same connector in Claude Code delivers the instructions whole, so support is per client and cannot be assumed. What reaches every client is, in order, the first sentence of each description, the full description once loaded, and tool results. So the ladder's top rung is a bonus, not the floor: each description opens with one sentence under eighty characters saying what the tool is for, and the `eval` description, the tool a model loads first, carries the orientation and the slips as well, at about 1.4KB, with the instructions kept whole beside it and the duplication accepted for clients that show both. The teaching errors carry the discovery pointers a blind model needs: a guessed `Host.*` name is sent to `Host.Code.print_modules()` rather than told to define it first, and the `Code`, `:code` and `Module` refusal names the listing beside the define tool, since the first thing a model with no instructions does is probe for what exists. A help tool and a `Host.help/0` were declined: a third tool costs every session on every client, and the guess it would answer is caught by the refusal at no cost.

**The first paragraph is the listing.** `print_modules` and the function index in `print_docs` render the first paragraph of a `Host.*` moduledoc and `@doc`, ExDoc's summary convention, so on a Host module that paragraph is one short sentence and the explanation starts in the second. Library and framework modules keep their own conventions and are listed by name alone.

### Login and OAuth

Settled 2026-09-21 in four phases, verified against clients 2026-09-22, the pages made LiveViews 2026-09-23.

**Why both a header and a browser flow.** ChatGPT connects a custom server by OAuth or not at all and says outright that it cannot present an API key; claude.ai offers an individual OAuth or nothing; Claude Code takes either; code takes a header only, since a server-side loop has no browser to complete a redirect. So the hosted chat clients need OAuth and the audience's own agents need a header token, and both stay. Rejected: a token in the URL path, which lands in every request log and is still a secret pasted into a third-party app, the thing OAuth removes; a stdio proxy on the user's machine, which reaches only clients that spawn local processes; a hosted authorization server such as Clerk, Auth0 or WorkOS, which would remove the issuing half at the cost of a third-party identity account as a runtime dependency of a self-hosted server, policy on the user because a provider's consent screen offers no choice, and an internet connection for local development, kept in view since Beamlet's resource-server side is issuer-agnostic and could later point at an external issuer; and the Elixir libraries, none of which fit a SQLite-backed single-tenant server issuing opaque tokens (`boruta` is Postgres and beta, `ex_oauth2_provider` has no PKCE, the rest are JWT-only or need Ash). The issuing half is a login, two endpoints, a consent page, a code store and a client-document fetch, and rolling it was a couple of days.

**Vocabulary.** The **client** is the app connecting and identifies itself by a **client id**. Beamlet plays both OAuth roles at one origin: the **resource server**, the MCP endpoint, and the **authorization server**, which issues tokens. **Protected resource metadata** (RFC 9728) names the authorization server; **authorization server metadata** (RFC 8414) names its endpoints and what it supports. A **client ID metadata document** (CIMD) is how a client registers without registering: its id is an https URL on its own domain serving a JSON document with its name and redirect URIs; **dynamic client registration** (RFC 7591), an unauthenticated endpoint storing clients in a table, is the older alternative the 2026-07-28 MCP revision deprecates. **PKCE** binds an authorization to the client that started it: a hash of a secret when asking, the secret itself when redeeming. An **authorization code** is the short-lived, single-use string the browser carries back after consent, worthless without the PKCE secret. The **access token** rides in the bearer header; the **refresh token** is redeemed for a new pair; **rotation** means a refresh token dies the moment it is used. The **resource** parameter (RFC 8707) names the MCP URL a token is for.

**Beamlet's own plug plays both roles; Anubis is the transport.** `Beamlet.MCP.Plug` wraps the transport plug with the server baked in, so `Beamlet.Router` mounts it with one forward. It runs on every request and method: reads the `Bearer` secret, the scheme matched in any case, authenticates it through `Beamlet.Tokens`, and puts the principal in the conn's assigns before forwarding; Anubis re-merges the conn's assigns into the frame on every message, so `frame.assigns.principal` in a callback is always the current request's, which is what makes identity per request rather than per session. A missing token, another scheme, an unknown secret or an `oauth` token past its expiry is a 401 whose `Bearer` challenge carries the realm `beamlet` and the `resource_metadata` URL, which is how a chat client discovers that this beamlet is its own authorization server; a token naming a policy the beamlet no longer declares is a 403 with a line naming both. Anubis's own authorization was weighed twice and lost twice: it would have needed a wrapper plug anyway for the transport's compile-time `request_timeout`, the public URL at server start, a guard for task-style tool calls whose frame carries no claims, and an idle Finch pool, and a validator failure is always a 401, so the 403 would go; matching what it does is one header parameter and one expiry clause. `Beamlet.OAuth` holds the shared facts, the issuer, the resource `/beamlet/mcp` and the two discovery documents, built at request time from the endpoint's `url` config, so the public URL is not a config key and is never needed at boot; `Beamlet.OAuth.MetadataController` serves the documents at the root (§ 2 Web).

**Login.** The owner signs in with their email and password, both set by `beamlet setup` (§ The owner, tokens and principals). The password is prompted for, never an argument, so it stays out of the shell history. Under `-noshell`, which is how `mix`, `elixir -e` and a release's `eval` all run, `:io.get_password/0` answers `enotsup`, so the CLI switches to OTP 28's raw no-shell mode for the read alone (`:shell.start_interactive({:noshell, :raw})`) and back after, since output printed while raw loses its carriage returns; when stdin is a pipe the read is a plain line. Hashing is `pbkdf2_elixir`: pure Elixir so the image needs no native build, the modular crypt format so the row is one string, a dummy verify so an unknown email, and a beamlet with no owner yet, cost the same as a wrong password, and a rounds setting the test config drops to one; `Plug.Crypto`'s key generator lost on having to write the salt, count, encoding and compare ourselves. At least eight characters, at most 128 bytes, and no other rule. The cap is in bytes because PBKDF2's cost grows with the password's byte length, and sign-in refuses a longer password with the same dummy verify as an unknown email rather than hashing it, since an unauthenticated POST of 100KB otherwise cost about nine seconds of CPU. The sign-in is a session row in the system database (`Beamlet.Session`, owned by `Beamlet.Owner`, with no reference to the user since there is one), and the browser holds its secret in the app's own cookie, `_beamlet_app_key` scoped to `/beamlet` and HTTP-only (2026-09-29). Every request turns the secret back into the owner, so a new email holds, and a new password or a sign-out signs out. The sign-in stays out of the host's cookie session because agent pages share it: an agent controller can `put_session`, or read `conn.secret_key_base` and sign a cookie offline, so an identity held there could be forged by any agent route and used to consent to a token under any policy. Agent pages keep the endpoint's session, which holds no identity, a forged signature still needs a secret that matches a row, and the system database is out of reach of the APIs agent code is given, though not contained against code trying to get past its policy (`context/security.md`). `Beamlet.Router`'s browser pipeline plugs the app's `Plug.Session` ahead of `fetch_session`, replacing the endpoint's before anything reads it, so the app's CSRF token, flash and return path live there too; the app's LiveViews connect to their own socket, since LiveView merges a socket's session into every mount on it and a shared socket would hand the app session to agent LiveViews. Private routes (§ 4) will need the owner recognised on agent paths without this cookie reaching them. `Beamlet.Web.Auth` is the whole of it: `session_options` for the cookie, `fetch_current_user` and `require_auth` as plugs, the latter storing a GET's path to return to, `on_mount` hooks of the same two names for a `live_session`, and `log_in` and `log_out`, which create and delete the session and renew the cookie. A sign-out disconnects (2026-10-01): `log_in` puts a `live_socket_id` naming the session into the app's session, which the app's LiveView socket takes as its id, and `log_out` broadcasts `disconnect` on it through the configured endpoint, so a page open in another tab reconnects, re-runs the auth hook and goes to the login, rather than a consent page that is still open being able to Allow on a session that is gone. A new password set by `setup` cannot do the same, since the CLI is its own VM with no way to the server's PubSub: the sessions are deleted, so the next reload or reconnect goes to the login, but an open page keeps its socket until then (roadmap, Deferred). The form is `Beamlet.Web.SessionLive`; it posts to `Beamlet.Web.SessionController`, which owns `/beamlet/logout` too, lands a sign-in on the stored path or `/beamlet`, and sends a failure back to the form with a flash. What the sign-in leaves open, no rate limit, no session expiry of its own, and script on an agent page driving the consent page as the signed-in owner, is accepted for 0.1 with the fixes chosen in `context/security.md` § Accepted risks.

**Client identity: metadata documents only.** No dynamic registration, no clients table, no unauthenticated write endpoint; the fallback is added the day a client proves it needs it. The metadata advertises `client_id_metadata_document_supported` and `none` as the token endpoint auth method, the pair claude.ai requires before it chooses CIMD. `Beamlet.OAuth.Clients` fetches the https URL a client gives as its id, requires the document's own `client_id` to equal it and a non-empty `redirect_uris`, each https, loopback http or a custom scheme outside `javascript`, `data`, `vbscript`, `file` and `blob` (the sent page follows a custom scheme through a link on the beamlet's origin, so a script scheme there runs as the signed-in person), reads nothing else, not even the display name, and caches it for an hour. A redirect URI must equal a listed one exactly, except that a listed loopback URI matches either loopback host on any port (RFC 8252 § 7.3), which is what Claude Code sends. The fetch is guarded by `req_ssrf`: https only, no address literals, every resolved address checked, a failed lookup refused, plus no redirects, five seconds and 64KB of the beamlet's own; it won over hand-rolled code and over `safeurl`, which is IPv4-only and passes a failed lookup, and it offers the resolver seam the tests need. The DNS rebinding window stays open, as the library documents, since pinning the connection to the checked address costs a Finch instance per hostname; login comes before the fetch, so only a signed-in person can make the beamlet issue a request at all. The test seam is `config :beamlet, Beamlet.OAuth.Clients, req_options: [...]`, empty in production, carrying the `Req.Test` plug and a resolver in test; a `Beamlet.Config` key lost on putting a test seam on the operator surface.

**The flow, endpoint by endpoint.**

1. **Discovery.** A client calls `/beamlet/mcp` with no token and gets the 401 naming the protected resource metadata URL. That document names this origin as the authorization server; the authorization server document at `/.well-known/oauth-authorization-server` names the two endpoints below and declares S256, the code and refresh grants, `none` auth, CIMD support and `iss` support.
2. **Authorize.** `GET /beamlet/authorize` with `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method=S256` and optionally `resource` and `scope`. A signed-out person goes to the login and returns to the same request, query string included. An unknown client or an unlisted redirect URI is an error page, since the beamlet cannot safely redirect; every other fault redirects to the client with `error`, `error_description`, `state` and `iss`. `resource` must equal the MCP URL when sent.
3. **Consent.** The person chooses a policy and allows or denies; a code is stored and the browser goes back to the client with `code`, `state` and `iss`, or with `access_denied`.
4. **Exchange.** `POST /beamlet/token`, form-encoded, no session and no CSRF check since clients post directly, `grant_type=authorization_code`. The code is looked up and deleted, the client id, redirect URI and `resource` checked against what it was issued for, the SHA-256 of `code_verifier` against the stored challenge, and `Tokens.create` mints with the consented policy. The JSON reply carries the access token, `token_type`, `expires_in` and the refresh token; errors are OAuth error bodies, `invalid_grant` and friends, because the client reads them.
5. **Refresh.** Same endpoint, `grant_type=refresh_token`: look up the refresh hash, check its expiry, rotate in place, reply with the new pair. A used, expired or `cli` token is `invalid_grant`.

`Beamlet.OAuth.Codes` is the store between consent and exchange: a GenServer holding pending codes with the policy, client id, redirect URI, challenge, resource and scope, ten minutes, single use, swept every minute, gone at a restart, which means `invalid_grant` and the person connects again.

**The consent page** is `Beamlet.OAuth.AuthorizeLive`, behind the login. The request is validated at mount and held in the page's state, the decision is an event, so the form carries no hidden fields and nothing to validate twice, and the consent, error and sent states are renders of one module; the error page answers 200, since a LiveView sets no status and no client reads that page. It names the client by its id's host and never shows the document's display name, lists every declared policy with its tools, `default` selected, has a Deny, warns when the redirect is loopback, and shows who is signed in. The way back depends on the redirect URI: http and https are a plain redirect, and a custom scheme, which is how a desktop app such as Raycast receives its code, renders a page with a meta refresh that sends the browser on and says the app has opened and the tab can be closed, since a redirect there opens the app and leaves the tab on the consent form.

**Lifetimes and scopes.** An access token lives a day and a refresh token thirty days, sliding: `Beamlet.Tokens.rotate/2` sets both from now and replaces both secrets on the same row, so a client in regular use never asks the person to consent again and the token id survives. Constants on `Beamlet.OAuth`, not config: revocation is delete, so a short access token would buy little. A row whose refresh has expired stays until the owner deletes it, and `beamlet tokens` shows the expiry. No scopes: none advertised, none understood, whatever the client sends is echoed in the token reply, which under RFC 6749 states what omitting it already implies. Claude Code requests the scopes the protected resource document lists and works without any; ChatGPT requests every scope the authorization server document lists and expects an exact echo; so listing none is what makes the consent page's policy choice the whole story. A one-scope or per-tool scheme lost: a scope that cannot be declined is decorative, and per-tool scopes would put a second permission axis beside the policy. No CORS and no dynamic registration until a client proves it needs them.

**Verified 2026-09-22** over a Tailscale funnel with every client on its defaults: ChatGPT connects and signs in smoothly; the Claude app's "use Claude's published identity" (CIMD) works, bouncing through a claude.ai page before the beamlet's consent; Raycast reaches for the metadata document and connects, and its custom-scheme redirect is why the sent page exists; the MCP Inspector detects the challenge but cannot run the flow itself, so it neither needed CORS nor proved it does. No client asked for registration and none tripped on the scope echo. Since the pages became LiveViews the flow has had a brief pass only; the four clients want another.

### Web

Settled 2026-09-17. The pages and APIs agents build are served by the host's own endpoint, named in config, and Beamlet owns the router that serves them, the layout they render in, and a plain error view.

**The app is Beamlet's own inner app** (2026-09-29): the sign-in, the consent page, the home page and the admin pages to come. The word names what belongs to it and to nothing agents build: its socket at `/beamlet/app/live`, its session cookie `_beamlet_app_key`, its root layout `app`, its stylesheet `app.css`. "Beamlet" in a name means what the agent side uses, such as the agent pages' socket at `/beamlet/live`. The split is what keeps the sign-in out of agent code's reach, so a new piece of the inner app takes the app's name and its own plumbing rather than sharing the agent side's.

**The host forwards at the root, last.** The one line a host writes is `forward "/", Beamlet.Router` as the last route of its router. Last because a root forward matches everything after it, so host routes win by order. At the root because LiveView's connected mount re-matches the full browser URL against the router that dispatched the page, stripping only the endpoint's script name, and `Phoenix.Router.route_info/4` never recurses through a forward; a forward at a prefix therefore breaks every LiveView page.

**Root by default, and a reserved namespace.** No prefix: "add a dashboard to my beamlet" is served at `/dashboard`. The beamlet owns every path whose first segment is `beamlet`: `/beamlet/mcp` for the MCP server, `/beamlet/live` and `/beamlet/app/live` for the LiveView sockets, agent pages' and the app's, `/beamlet/assets/...` for the JavaScript and the stylesheet, `/beamlet/login` and `/beamlet/logout` for the sign-in, `/beamlet/authorize` and `/beamlet/token` for OAuth, `/beamlet` for the home page and later the admin pages; a first segment of `beamlet` is refused at mount. The refusal teaches; the guarantee is `Beamlet.Router`'s, which answers 404 for any path under `/beamlet` it has no route of its own for, ahead of the forward, so no agent route answers there whatever `__routes` holds: a param or glob first segment, a path whose empty segments Phoenix collapses into `/beamlet/...`, or a raw row (2026-09-29). Without it, every `/beamlet` path or verb the beamlet lacks would fall through to agent routes: a look-alike sign-in on the real origin, and the app's cookie, scoped to `/beamlet`, handed to agent code. One named segment rather than an underscore marker (2026-09-21): a marker suited paths no person types, and once the beamlet had pages for a browser, `/_/login` read as a mistake where `/beamlet/login` reads as what it is. The cost is that an agent cannot mount `/beamlet`, a page nobody was going to build. The prefix survives as an embedder's option, `config :beamlet, web: [prefix: "/app"]`, for a host that wants agent-built pages fenced under its own namespace; the generated router bakes it into its scopes, since a forward cannot supply it. The beamlet's own paths never take the prefix. The one beamlet-owned surface outside the segment is the pair of OAuth discovery documents, which the specs fix at `/.well-known/oauth-protected-resource`, also served with `/beamlet/mcp` appended since clients try that form first, and `/.well-known/oauth-authorization-server`: three exact routes in `Beamlet.Router` ahead of the forward. `.well-known` is not a reserved segment, since an agent may have its own use for the directory; the three paths win by order.

**Two routers.** `Beamlet.Router` is static and public: it carries the beamlet's own routes under `/beamlet`, the MCP plug, the sign-in and the home page, and forwards everything else to `Beamlet.DynamicRouter`, so the beamlet decides what lives under `/beamlet` and the host's line never changes. Because it sits behind a root forward, it carries LiveViews directly, with no router macro. `Beamlet.DynamicRouter` is the generated module: a compiled-in empty placeholder, so the forward compiles, that `Beamlet.Routes.regenerate/0` replaces in the VM by building the route table into a real `Phoenix.Router` as quoted form (`Beamlet.Routes.Generator`, internal) and compiling it, both inside `Beamlet.Code.compile_artifact/2`. Quoted form rather than source text (2026-09-29): a row's path goes in as a binary and its module and action as atoms, so nothing a row holds can become code, which matters because agents write `__routes` with raw SQL and the library's compile is not scanned. A derived artifact: never on disk, never committed, rebuilt from the table at boot and after every change. Two convention pipelines, LiveView rows through a browser pipeline with session, CSRF protection and the root layout, controller rows through an API pipeline with neither so a webhook can call them; no plug kind, no per-mount override. Rows render in mount order, each run of one kind in its own scope through that kind's pipeline, so an earlier mount wins an overlapping match as in a hand-written router, whatever the kinds (2026-10-02). A row's module and controller action resolve to existing atoms only, so a raw row naming something never loaded makes no atom; a live action names no function, so it is made into an atom, but only for a row whose target is a defined LiveView. The generated router lists the rows it was built from (`__served__/0`), so `Beamlet.Routes.served?/1` answers what the router in the VM really serves. Folding the static routes into the generated source lost: it couples the MCP mount to an artifact that fails and rolls back.

**The table.** `Beamlet.Routes` is the context over `__routes` in the agent database, with `Beamlet.Route` at the root beside it: kind, verb, path, module in inspect form, an optional action, the principal as JSON and `inserted_at`, unique on verb and path with a LiveView storing `get`. The format validations, with Plug's own reading of the path so a path Phoenix would refuse (a glob before the end) never reaches the build, run on insert and again at generation (`Beamlet.Route.load_changeset/1`), since raw SQL skips the changeset. A malformed row is deleted at generation, with a warning recording the whole row: only raw SQL can write one, nothing an agent defines can make it valid again, and while it stands it holds its verb and path against a real mount. Rows are read as raw columns and loaded one at a time, so a row Ecto cannot load at all (an unknown kind or verb, a principal that is not JSON) is skipped by every read and deleted at generation the same way, rather than making every read raise (2026-10-02). Neither has its own annotation in `print_routes`: raw SQL is not how routes are mounted, so the cheapest handling that keeps routing working is the whole of it. The deletion is for rows that were never valid; a change that tightens the validations ships a furniture step deciding what happens to existing rows it would fail, so an upgrade never quietly deletes routes that were valid when mounted. `create`, `delete` and `list` change or read the table and nothing else; regeneration, which may delete malformed rows, is the caller's to compose, which `Host.Router` does by inserting, regenerating and deleting the row again when regeneration fails. A define can repair a route's target or break one without touching the table, so `Beamlet.Define` and `Beamlet.Patch` compose `Beamlet.Routes.refresh/0` after theirs, which rebuilds only when a row's servability and the router disagree; redefining a routed module that stays servable compiles nothing, since the router names the module and the new version serves. A failed rebuild is a warning on the define's summary, not an error, since the define stands (2026-10-02). A row that is malformed, or whose target is not a module defined with `define`, is missing, quarantined or of the wrong shape, is left out at generation with a warning and answers 404; the row stays for inspection, and `servable?/1` is the one rule generation and `print_routes` share. Remove does not use it: it refuses while any row names the module, served or not, so a route that is down for now keeps its target. Requiring a defined target keeps a row from serving one of the beamlet's own LiveViews through the agent pipeline, past its sign-in hook. The boot child is synchronous, right after the code server, returns `:ignore` and never fails the boot: the worst case is the placeholder serving 404s with an error in the log. An empty table and an empty loaded router already agree, so boot compiles nothing in that case, which is what keeps a suite that boots a beamlet per test from paying a forty-millisecond router compile each time.

**What the host carries** is written down twice: as the list of integration points on `Beamlet.Router` and as `Beamlet.TestEndpoint` in the library's test support, which `Beamlet.Case` starts after every beamlet and the server app copies. In the router, the root forward; in the endpoint, the session agent pages use, the LiveView socket for agent pages at `/beamlet/live` and the one for the app at `/beamlet/app/live`, which names `Beamlet.Web.Auth.session_options/0` as its session, `Beamlet.Assets` and the JSON and urlencoded parsers, the latter for the sign-in form and the token endpoint; in config, the endpoint named under `:web`, `pubsub_server: Beamlet.PubSub` and `render_errors`. `Beamlet.Assets` is a `Plug.Builder` over three `Plug.Static` plugs under `/beamlet/assets`: the LiveView JavaScript from the deps' precompiled bundles, so there is no JavaScript build, and the beamlet's own stylesheet from the package's `priv/static`; it is a plug on the host's endpoint rather than a forward inside `Beamlet.Router` because agent-installed JavaScript (§ 4) may grow it and how it is consumed is reviewed then. The web pieces live under `Beamlet.Web`. `Beamlet.Web.Layouts` holds two root layouts, named for whose pages they carry: `beamlet` is the agent pages', CSRF token, the two modules, the agent socket, Tailwind from its CDN, and nothing about how a page looks, styling needing the internet being accepted for a substrate with no bundler; `app` is the app's root, the same wiring with the app's socket and the built stylesheet in place of the CDN. Inside it, `split/1` is the layout for the sign-in and consent pages, the panel with the wordmark, a tagline and the beamlet's address beside the form, and `shell/1` the signed-in pages', the top bar with the host, the owner's email and the sign-out. `Beamlet.Web.ErrorView` renders a status message as text or as JSON, so a miss under the forward is a plain 404 and the test endpoint and the server need no error view of their own; the HTML 404 adds one sentence saying the beamlet has its own pages at `/beamlet`, since `/` is a miss until an agent mounts it. A host with its own error view keeps it.

**The app is styled by a built stylesheet** (2026-09-22). The sign-in, the consent page and the home page are the app's, so they need no build step of the host's: the `tailwind` hex package, a standalone binary with no Node, builds `assets/css/app.css` into `priv/static/app.css`, Tailwind v4 scanning the directories the app's markup lives in, `lib/beamlet/web` and `lib/beamlet/oauth` for the consent page, for classes (the whole of `lib/beamlet` was scanned until 2026-09-30, which picked up words in prose as classes), and the output is committed, as `phoenix_live_dashboard` ships its stylesheet, so the hex package, a git dependency and the Docker image all carry it with no extra step. `mix assets.build` refreshes it and `precommit` runs that beside `format`, so the file cannot drift; the dependency is dev and test only, never runtime. The server's dev config has one watcher, which runs the library's mix task in the library directory with `--watch`, so one config owns the build. Development reloads the library as well as the server: the endpoint names `:beamlet` among its `reloadable_apps`, so a request recompiles a changed template, and `phoenix_live_reload` watches the library's directory beside the server's, set by absolute path in `config :phoenix_live_reload, :dirs` since its default is the server's root alone; a stylesheet change swaps in place and a template change reloads the page. The pattern for new views is a Claude Design mockup, an implementation from it, then hand refinement against the live page. No JavaScript pipeline: an entrypoint and esbuild were weighed and put off until a page needs a hook, likely the admin pages, since without colocated hooks a bundle would carry nothing the raw modules do not. Agent pages keep the CDN and the raw modules, and their layout paints the canvas (2026-09-29): the body carries a background and text colour for light and dark, following the system setting as Tailwind's `dark:` does, since agents write `dark:` classes on the assumption that the layout handles the page behind them and a bare body left light text on white. `Host.Web` says so in a sentence.

**The design language is the design system's tokens, not its components** (2026-09-22). The Beamlet design system lives in Claude Design, far larger than the pages need, and the codebase takes from it in the order a page asks. `assets/css/app.css` carries a Tailwind `@theme` that replaces Tailwind's palette with the putty, slate, rust, phosphor and ochre ramps and names roles over them (page, card, strong, body, muted, faint, link, primary, danger, hairline, line), plus the three fonts, the type scale, the radii, the hard offset shadows and the fast easing, and a base layer for the page ground, headings, links, inline code and the focus ring. Replacing the palette is the point: a page can only name colours the language has, so drift shows as a class that styles nothing. The fonts load from Google Fonts with system fallbacks, as the CDN already does for agent pages; packaging them is open. `Beamlet.Web.Components` holds a piece once a second page needs it: wordmark, button, input, flash, code panel and numbered steps so far. Icons stayed out.

**Every view is a LiveView** (2026-09-23). A template lives in a render function or a function component and nowhere else: no static `.heex` files, no `_html` view modules, one way HEEx works across the beamlet's pages, and the admin pages to come are LiveViews anyway. What is not a view stays a controller: the session writes in `Beamlet.Web.SessionController`, the token endpoint and the metadata documents. The sign-in LiveView renders the form and posts it to the controller, as `phx.gen.auth` does, because a session cookie is written on an HTTP response. The consent LiveView holds the request in its state and takes the decision as an event. Accepted: the consent page needs the socket up before Allow does anything, which the long-poll fallback covers; every client tested opens the page in the person's default browser, not an embedded one.

**The home page** (2026-09-22) is the setup page at `/beamlet`, behind the login: the MCP URL with a copy button, then one client at a time under tabs chosen by the `client` query parameter, so a tab has a URL. Apps, Claude and ChatGPT by name and any other OAuth client, connect by signing in on the consent page. Coding agents that offer OAuth sign in from the terminal with their own commands. Everything else, Cursor, a project's `.mcp.json` and code calling the Claude or OpenAI API, sends a `cli` token in a header, and the page shows the `beamlet tokens.create` command to run. The rule is OAuth where a client offers it and the header everywhere else. The page mints nothing and lists nothing: self-service tokens and the token list wait for the admin pages in 0.4, and management stays on the command line. No plan or pricing claims, since which plans can add connectors changes without notice; the page gives the menu path and the form fields as of writing. `mcp-remote` for stdio-only clients is off the page until someone cannot connect without it. Copy on these pages is reviewed by a human read, not pinned by tests; a view test asserts on structure and behaviour.

**The agent face** is `Host.Web` and `Host.Router`. `use Host.Web, :live_view | :controller | :live_component | :html` is the one `use` line an agent writes; it brings the framework for the role, `Phoenix.HTML`, the `JS` alias and `~p`, and an unknown role is a teaching error at define time. `Host.Router` holds the verbs, `live/3` and the five named for HTTP verbs, `unmount/2`, `path/1`, `url/1`, `~p`, `call/4` and `print_routes/0`. Two words kept apart: a *path* is what the agent chooses and every function takes, never carrying the operator's prefix, and a *URL* is what people are given; `path/1` and `~p` map the one to the browser path and `url/1` to the other, and a path that already carries the prefix is refused with the relative form suggested, only when a prefix is set. A mount validates the path (a string, a leading slash, the row's format, no empty segments, since Phoenix collapses them and `/a//b` would be served at `/a/b`), refuses a reserved first segment with copy naming the convention, requires the target to be in the code server's manifest and of the right shape (`__live__/0`, or `action/2` plus the action), then composes `Beamlet.Routes`: insert, regenerate, delete the row if the router failed to build. Mount and unmount require the ambient principal and the row records it; a conflict names the mounted route and the token that mounted it. `print_routes` prints the base once, then verb, path, target, mounting token, and a not-served annotation from `servable?/1` and `served?/1`, so it never claims a route the router lacks.

`call/4` is a real request through the configured endpoint over `Plug.Test` in the calling process, the response returned as data with JSON decoded, the adapter's mailbox messages drained so they never reach a LiveView's `handle_info`, and a crash re-raised with the route's frames above the endpoint. It sets the ambient principal aside for the dispatch and restores it after (`Beamlet.Principal.delete_current/0`), so a route behaves under `call/4` exactly as it does in a browser: a served route acts as nobody, and a controller action that reaches for `Host.Code` or the mutating verbs raises either way. Without that, an agent's test call would pass where a visitor's request fails.

**Every dynamic route is public.** The login guards the beamlet's own pages, never an agent's; private routes stay open in § 4.

### Deployment

Settled 2026-09-18: a release in a Docker image. The server app is endpoint, application module and config under one `BeamletServer` namespace, no tests of its own. The image is multi-stage on the hexpm Debian builder and the matching slim runner, since the release carries ERTS and the SQLite NIF built against the builder's libc; the runner adds git, which the code audit shells out to, and runs as the `beamlet` user, uid 1000. The release keeps the Docs chunk (`strip_beams: [keep: ["Docs"]]`), since `print_docs` and the policy's `@moduledoc false` filter read it, and always serves: no `PHX_SERVER` toggle. The operator surface is a volume and six variables: `BEAMLET_DATA_DIR`, `/data` in the image, holds everything including the cookie secret, generated on first boot into `secret_key_base` when `SECRET_KEY_BASE` is unset; `BEAMLET_URL`, one variable for host, port and scheme, which LiveView's origin check and the OAuth issuer key on; `PORT`; and the three timeouts (2026-09-30), `BEAMLET_EVAL_TIMEOUT`, `BEAMLET_DEFINE_TIMEOUT` and `BEAMLET_MCP_REQUEST_TIMEOUT`, in milliseconds as config takes them, each setting its key only when set so the defaults stay in `Beamlet.Config`. TLS is the proxy's: `force_ssl` is compile-time config and would break plain HTTP on a LAN, so it is out, and `Plug.RewriteOn` reads the forwarded scheme so the session cookie is marked secure behind the proxy. `bin/beamlet` is an overlay script over the release's `eval`, which passes trailing arguments to `System.argv/0`, runs the config providers and loads the release without starting it; the CLI starts the system half itself, so the script works on a fresh volume and beside a running server. `fly.toml` at the root is one machine in one region with the volume at `/data` and auto-stop off, since a beamlet's modules are compiled into the running VM. The library's only declaration surface is application config, so the release merges an optional operator config file, `<data_dir>/config.exs`, into it at boot through `Beamlet.Config.Provider` (settled 2026-09-23): a plain `import Config` file, one file with imports disabled, read after `runtime.exs` and merged over it, so the file is the last word; absent means nothing, silently; one that fails to evaluate fails the boot naming the file and the line, which the provider takes from the compiler's diagnostics since Elixir reports an undefined name as a line-zero error. The file is for the beamlet's own keys, the policies above all, but it is ordinary application config and can set any key of any application, the environment's included; the docs say that is not the intended use rather than the code preventing it. The stance: the environment configures the deployment, the file configures the beamlet, with the timeouts in both, since tuning one should not mean writing a file, and the file's value winning where both set one; wanting more is wanting a different host, which is the child spec in your own application. Restricting the file to `:beamlet` was weighed and dropped as a rule for nothing. The release's `eval` runs the providers, so `beamlet policies` in the container reads the file afresh and is the check, before any restart. The operator loop is the same on Docker and Fly: write the file locally, put it on the volume (`docker cp` into the container, whether running or stopped; `put` in `fly sftp shell`), run `beamlet policies`, restart, create the token with `--policy`. The image has no editor, and the file must stay readable by uid 1000, which `docker cp` preserves from the local mode.

**Publishing** (2026-09-23). A version tag (`v0.1.0`, `v0.1.0-rc.1`) publishes the image to `ghcr.io/aaronrussell/beamlet` through `.github/workflows/release.yml`, which first runs the CI workflow and refuses a tag that differs from the version in either `mix.exs`. amd64 and arm64 build on native runners, since an emulated Elixir build is too slow, and merge into one multi-platform image. A release is tagged with its version and its minor (`0.1.0`, `0.1`) and moves `latest`; a pre-release gets its version alone; the major tag waits for 1.0; nothing tracks `main`. `latest` is the most recently pushed release, not the highest version, which differs only if a patch ships to an older minor. `fly.toml` deploys the published image pinned by version, so the Fly beamlet runs exactly what was released and a deploy is a choice of release. The hex package is published by hand.

## 4. Deferred

- Admin UI. The admin LiveViews sit in `Beamlet.Router` under `/beamlet`, beside the home page and behind the login, with the password asked again for sensitive actions, the consent page's Allow among them (roadmap 0.4).
- Private routes, which only the owner can reach. A property of the mount, `private: true`, never of the path or the controller, keeping one namespace with the generated router putting the row in a scope that requires the signed-in owner. Access keys on the web identity, never the principal (§ 2 The owner, tokens and principals). The app's cookie stays scoped to `/beamlet` so the app's session never reaches agent code, so a private route needs a second, weaker cookie on agent paths, one that admits the owner to private routes and to nothing of the app's.
- A principal handed in by an embedding host calling tools in-process, without a Beamlet token. If it returns, a principal that encodes and decodes is the seam.
- Virtual paths on `Host.File`: a `~name/` prefix, which cannot collide with an agent's directories and which `Path.expand` leaves alone, resolved through a mount table from prefix to directory and mode; a read-only mount refuses writes with a teaching error and lists beside ordinary entries. The first candidate is `~docs/` over the package's `priv/docs`, documentation for agents served as read-only files, each page under eval's output cap. Kept deferred because every convention so far found a module to own it, and a wiki with three pages is a second discovery surface the instructions would have to spend bytes pointing at. The trigger is a topic with no owning module, an end-to-end tutorial or operator notes, or a Host moduledoc outgrowing about 4KB. MCP resources are the other shape for documentation and lost to the rule that everything is reachable through `eval`.
- Atoms in KV values, as map keys and as values. The likely shape is a tagged map, `{"$map": [[k, v], ...]}` with `{"$atom": "name"}` for an atom, emitted only for a map with a key that is not a string, so a plain map stays plain JSON. Atoms decode with `String.to_existing_atom/1`, so an atom known only to a since-removed module fails to load, and a stored module name comes back as data, which the scanner does not follow (`context/security.md`). Tuples and structs stay out.
- Supervised processes for agent code (roadmap 0.2).
- Protocols: agent-defined protocols and agent implementations of library ones, `defprotocol`, `defimpl` and `@derive`, all refused today (roadmap, Deferred).
- Agent-installed dependencies, and with them who grants an installed package to agent code (roadmap 0.5).
- Package-level denial in a policy (`deny_app`) and reloading policies without a restart, each when a policy needs it.
- A `capabilities:` key in a policy naming `eval` and `code`, with a `code:` config key for the compile timeout, in place of `tools:` naming `eval` and `define` with `define` granting two tools; may read clearer once there are more tools (2026-09-29).
- Static assets, and agent-installed JavaScript and CSS, with colocated JS and CSS in agent modules as the likely shape (roadmap 0.3). `Beamlet.Assets` is where served files would grow. Colocated CSS needs `config :phoenix_live_view, root_tag_attribute:` set in the VM that compiles the module, which for agent modules is the beamlet's, so the setting is the library's to make or require of every host, not the server's; and both extract to files under `_build` that a bundler is expected to pick up, which the no-bundler substrate would have to serve itself.
- A hosted or external OAuth issuer in place of Beamlet's own, which the issuer-agnostic edge allows.
- The modern-era MCP protocol (2026-07-28); Anubis 2.0 is legacy-era and current clients negotiate it.
- Any dependency on Omni packages. If `omni` is ever added, it is as a library for agents to use, not as a foundation.
